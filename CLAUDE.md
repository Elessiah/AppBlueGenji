## Project Overview

BlueGenji Esport is a French esports platform for amateur Marvel Rivals and Overwatch tournaments. It manages tournaments, team/player profiles, and integrates with a Discord bot.

## Commands

```bash
npm run dev          # Dev server with Turbopack
npm run build        # Production build
npm run lint         # ESLint
npm test             # Jest test suite
npm run test:coverage

```

## Architecture

### Stack
- **Next.js 15** (App Router), React 18, TypeScript strict mode
- **MySQL 8+** via `mysql2` — no ORM, raw queries with auto-migration on first API access (`lib/server/database.ts`)
- **CSS Modules + `app/globals.css`** (aucun framework utilitaire), Radix UI Slot, Lucide icons

### Route Layout
- `/` — Landing page
- `/connexion` — Passwordless login (Google OAuth + Discord 6-digit code via DM)
- `/regles` + `/regles/[slug]` — Règles publiques de chaque mode de tournoi (schémas SVG inline). Contenu et mapping format → page dans `lib/shared/tournament-rules.ts` ; ajouter un mode = ajouter une entrée au registre (les pages sont pré-générées via `generateStaticParams`). Le bouton flottant « ? » des pages de tournoi (`components/rules/RulesHelpFab.tsx`) résout sa cible depuis le format du tournoi.
- `/(secured)/*` — Auth-protected routes: `tournois`, `equipes`, `joueurs`, `profil`
- `/api/*` — REST API routes (no tRPC, no server actions)

### Auth System (`lib/server/auth.ts`)
Sessions are stored in `bg_user_sessions` with SHA-256 hashed tokens, 30-day TTL, cookie `bg_session` (httpOnly, sameSite=lax). Quatre chemins d'entrée, **aucun mot de passe** :
1. **OAuth Google** — `/api/auth/google/{start,callback}`
2. **OAuth Discord** — `/api/auth/discord/{start,callback}` (certifie le tag au passage)
3. **OAuth Blizzard** — `/api/auth/blizzard/{start,callback}` (renseigne le BattleTag)
4. **Code Discord** — bot sends 6-digit code via DM, user submits at `/api/auth/discord/verify`, expires in 10 min

**Google One Tap** (`lib/server/google-one-tap.ts` + `app/api/auth/google/one-tap/route.ts` + `components/auth/google-one-tap.tsx`) : une cinquième route, pas un cinquième compte — c'est la même porte Google que la première, atteinte sans quitter la page. Le script `accounts.google.com/gsi/client` rend directement au navigateur un JWT signé (`credential`), sans passer par notre serveur pour l'obtenir : le site doit donc le **vérifier lui-même** (signature RS256 contre les clés publiques de Google, `iss`, `aud` comparé à `GOOGLE_CLIENT_ID`, `exp`) avant de rejoindre le même `createOrGetOAuthUser` que les trois autres portes. Montée dans `app/layout.tsx` pour tout visiteur sans session ; nécessite d'ajouter l'origine du site aux « Authorized JavaScript origins » de la console Google Cloud, une case distincte du `redirect_uri` de l'OAuth classique. Quatre ouvertures nommées dans la CSP (`script-src`, `frame-src`, `connect-src`, `style-src` — l'invite est la seule iframe du site). Voir `docs/features/GOOGLE_ONE_TAP.md`.

**Trois portes, une seule mécanique** (`lib/server/oauth-flow.ts` + registre pur `lib/shared/oauth-providers.ts`) : jeton anti-CSRF, cookie d'état `bg_oauth`, filtrage de la destination, refus lisible quand la configuration manque, distinction `LOGIN`/`LINK`. Les six routes tiennent en cinq lignes et ne font que **nommer leur porte** ; ce qui distingue les fournisseurs se réduit à l'URL d'autorisation, l'échange du code et la forme du profil, isolés dans un client par fournisseur et normalisés en une `OAuthIdentity`. Trois copies auraient divergé sur le seul point où la divergence ne se voit pas. **On ne demande que ce qui sert** : `openid profile` (Google), `identify` (Discord), `openid` (Blizzard) — ni adresse, ni liste de serveurs ; les photos sont **copiées** chez nous, jamais relayées.

**Un compte ne se revendique plus par son adresse.** `createOrGetGoogleUser` rattachait une identité neuve à un compte existant sur la seule égalité de chaîne de l'e-mail : contrôler `email_verified` avait rendu ce rattachement honnête, il restait que le site décidait qu'une adresse *est* une personne, sur la foi d'un fournisseur dont il n'est pas l'émetteur. Le geste qu'il rendait — « j'entre par Discord, je veux aussi entrer par Google » — se fait là où il se prouve tout seul : **« Applications connectées »** sur `/profil`, où le joueur est *déjà connecté* quand il rattache. Corollaire assumé : le scope `email` a disparu, `bg_users.email` n'a plus aucun lecteur — et la colonne a fini par disparaître, avec les adresses qu'elle gardait (voir `docs/DATABASE_SCHEMA.md`), et deux connexions différentes d'une même personne donnent désormais **deux comptes** tant qu'elle ne les a pas rapprochés elle-même.

**Deux règles, dans `lib/server/account-identities.ts`.** *On ne déplace jamais une porte* : un compte dont l'identité d'un fournisseur est posée la garde (`PROVIDER_ALREADY_LINKED`), et une identité détenue ailleurs est refusée (`IDENTITY_ALREADY_LINKED` — `SELECT` pour le refus lisible, index unique pour la course). *On ne mure jamais la dernière* : sans mot de passe ni récupération par courriel, retirer le seul moyen d'entrer **ferme** le compte — refus en **409**, écrit une fois dans le module pur `lib/shared/account-connections.ts` que partagent l'écran (qui met la phrase à la place du bouton) et la route. Détacher Discord **efface la certification et garde le tag** (la preuve est partie, le tag redevient une saisie invisible de tous) ; le BattleTag, lui, survit à Blizzard — il n'est ni une porte ni une attestation.

**L'intention est scellée à l'aller**, jamais relue dans l'URL du rappel : lue là, elle serait choisie par l'appelant, et un `intent` retourné en `LOGIN` transformerait un rattachement en **changement de session**. La session est tout de même relue **au retour** (dix minutes séparent les deux), et le cookie porte le **fournisseur** : unique pour les trois portes, c'est le seul contrôle qui empêche un état obtenu sur l'une d'être reçu sur une autre. Voir `docs/features/OAUTH_PROVIDERS.md`.

**Se connecter par Discord certifie le tag — par le bouton comme par le code.** Un aller-retour OAuth mené jusqu'au bout *est* la preuve que demande la certification, et une meilleure que le code : c'est Discord qui nomme l'identifiant et le pseudo. Le pseudo retenu est `username` (stable, celui par lequel on retrouve quelqu'un) et non `global_name` (décoratif, partageable). **Le code par message privé reste** et garde sa raison d'être : il sert le membre du serveur BlueGenji qui préfère ne pas passer par un écran de consentement — la page de connexion nomme enfin ce chemin (« OU CODE PAR MESSAGE PRIVÉ ») au lieu d'un « OU » qui le faisait passer pour une variante du bouton juste au-dessus.

**Blizzard écrit le BattleTag, et l'écrase à chaque connexion.** Il n'a pas de colonne à lui : il *est* `bg_users.overwatch_battletag`, le champ déjà saisissable sur `/profil` — en ouvrir une seconde donnerait deux BattleTags pour un joueur, dont un faux. Entre ce que Blizzard affirme et ce qu'un joueur a tapé, la source fait foi (un tag mal recopié ne se voit pas, il se constate quand l'ajout en jeu échoue). `visible_overwatch` n'est **pas** touché : la connexion corrige une donnée, elle ne publie rien ; et un compte Battle.net sans BattleTag n'efface rien.

**Le code Discord est un secret, et un secret se compte — en base.** Six chiffres font un million de combinaisons : sans borne sur les essais, c'est une porte ouverte, pas un facteur d'authentification. La colonne `attempts` existait depuis toujours et n'était **relue nulle part** — elle s'incrémentait sans jamais rien refuser —, et aucun plafond ne couvrait `/api/auth/discord/verify` : un tiers connaissant le pseudo Discord d'un joueur (public sur n'importe quel serveur) pouvait demander un code puis énumérer jusqu'à ouvrir sa session.

Deux bornes tiennent le secret, **toutes deux en base**, parce que c'est le seul endroit où elles valent pour tous les processus et où l'on ne peut pas les faire oublier : `MAX_DISCORD_CODE_ATTEMPTS` (5 essais par code, le cinquième le **brûlant**) et `MAX_DISCORD_CODES_PER_WINDOW` (5 codes par compte et par quart d'heure). L'essai se **réserve en une seule instruction** — `UPDATE … SET consumed_at = CASE WHEN attempts + 1 >= ? THEN NOW() ELSE consumed_at END, attempts = attempts + 1 WHERE id = ? AND consumed_at IS NULL AND attempts < ?`, puis `affectedRows` : le quota lu sur la ligne déjà chargée puis décompté par une écriture séparée laissait un `await` entre les deux, et dix vérifications lancées de front lisaient toutes `attempts = 0`, passaient toutes le contrôle et comparaient toutes une combinaison (dix essais accordés pour cinq annoncés, jusqu'à la taille du pool — la course était sur la **lecture**, que le `CASE` ne pouvait pas fermer). Le `CASE` précède tout de même l'incrément, MySQL évaluant les affectations de gauche à droite. Un essai est donc décompté même sur un code juste, sans conséquence : la réussite consomme la ligne.

Les plafonds de débit sont une **première ligne gratuite, pas la garantie** : `lib/server/rate-limit.ts` compte dans une `Map` d'un seul processus dont le seau se vide entièrement (`bucket.clear()`) dès qu'on lui fabrique dix mille clés — et la clé est ici un identifiant Discord que l'appelant choisit. `DISCORD_CODE_REQUEST_RULE` (3 / 15 min) porte sur le **compte visé** — ce qu'il protège est le téléphone de la victime, que chaque appel fait vibrer ; `DISCORD_CODE_VERIFY_RULE` (10 / 15 min) porte sur le **couple (compte visé, IP appelante)** ; `DISCORD_CODE_REQUEST_IP_RULE` (120 / 15 min, large — une IP n'est pas une personne, un tournoi en réseau local sort tout entier par la même) porte sur l'IP et a un rôle propre : il est posé **avant** `resolveDiscordUser`, seul moyen de borner l'appel sortant vers le bot — qui interroge Discord — que cette route anonyme déclenche à chaque fois. La table, elle, se purge de ses codes expirés depuis un jour à chaque création (rien n'en effaçait jamais une ligne).

Un code neuf **rend le précédent inatteignable par sa seule existence** — `verifyDiscordChallenge` ne lit que le **dernier émis** —, donc rien n'est écrit et rien ne peut échouer à mi-chemin ; c'est le geste symétrique qui compte, un envoi raté **supprimant** sa ligne (`discardDiscordChallenge`), sans quoi la mort-née resterait la dernière et masquerait le code que le joueur tient de sa demande précédente, refusé comme invalide en lui brûlant ses cinq essais. Rien n'est invalidé *avant* l'envoi, pour la raison inverse : l'ancien tué et le neuf jamais reçu laissaient le joueur sans rien quand le bot redémarrait. **Les deux bornes se réservent, elles ne se relisent pas** : l'émission d'un code avait la même forme que le quota d'essais avant correction (`SELECT COUNT(*)`, `await`, `INSERT`), sur la borne présentée comme celle qui tient réellement la force brute — comptage et insertion vivent donc sous un **verrou nommé** par compte (`lib/server/named-lock.ts`, extrait de `migration-lock.ts`). Pas une transaction à `SELECT … FOR UPDATE`, et c'est une vraie base qui l'a tranché : sur la plage **vide** d'un compte sans ligne, chaque transaction pose un verrou d'intervalle sur la même plage puis demande, pour insérer, une intention qui entre en conflit avec celui des autres — douze demandes de front rendaient onze `ER_LOCK_DEADLOCK` et **un** code, là où cinq étaient attendus. Un verrou nommé n'a ni intervalle ni ordre de prise. Le plafond de *vérification* est enfin posé sur le couple **(compte visé, IP appelante)** et non sur le seul compte visé : la route est anonyme et l'identifiant Discord se lit dans la réponse de la demande, si bien que dix codes bidon fermaient la connexion d'un joueur nommé pour un quart d'heure — l'axe de la victime protège son téléphone à la *demande*, il la punit à la *vérification*. Comparaison en temps constant (`crypto.timingSafeEqual`) — deux empreintes de longueur fixe, rien à en tirer, mais un secret ne se compare pas avec `===`.

**Le revers, assumé** : qui connaît le pseudo Discord d'un joueur peut brûler ses codes et épuiser ses quotas, donc le tenir hors du chemin « code par message privé » par fenêtres d'un quart d'heure. C'est le prix de tout plafonnement d'un code à usage unique, très inférieur à celui d'une session ouverte par énumération, et chaque demande laisse une trace chez la victime, qui reçoit le message privé. Il s'est allégé depuis : un compte né par Discord garde la porte **OAuth Discord**, qui ne dépend ni du bot ni d'un message privé.

**Connexion Google — l'adresse n'entre plus dans le compte.** Le rattachement d'une identité Google neuve à un compte du site se faisait sur la seule égalité de chaîne de l'adresse : sans `email_verified` (renvoyé par l'`userinfo`, et jeté), obtenir une identité Google affirmant l'adresse d'un membre ouvrait sa session en un clic. Contrôler ce champ avait rendu le rattachement honnête ; il a fini par disparaître tout entier — voir la section « Auth System » ci-dessus, et `docs/features/OAUTH_PROVIDERS.md`. Il reste de cet épisode une leçon que la colonne **unique** avait rendue coûteuse : y écrire une adresse non vérifiée détenue par autrui ne la volait pas, elle faisait échouer l'insertion, `ER_DUP_ENTRY` avalé en `?error=oauth` à chaque essai, donc un compte inatteignable par Google pour toujours. Une identité venue d'un fournisseur n'est une preuve que de ce que le fournisseur atteste, et jamais de ce qu'on en déduit.

**Certification du tag Discord — un tag prouvé, et lui seul, est exposé à l'organisation** (`lib/shared/discord-identity.ts` pur + `lib/server/discord-verification.ts`) : un tournoi ne se gère pas sans joindre les joueurs (reprogrammer une manche, trancher un litige, confirmer un forfait), et `bg_users.discord_pseudo` était à la fois **invisible de tous** (`getFullProfile` ne le rendait qu'à son titulaire) et **invérifiable** — une chaîne libre où l'on pouvait écrire le tag d'un autre, un arbitre écrivant alors au mauvais joueur sans jamais l'apprendre. La certification règle les deux à la fois, et `discord_verified_at` est la charnière : **un tag non certifié garde les propriétés sous lesquelles il a été saisi** — invisible de tous, administrateurs compris —, sans quoi on changerait rétroactivement la finalité d'une donnée déjà collectée. Le public est décidé par `canViewDiscordTag`, dont **l'ordre des cas est la règle** : soi-même toujours ; *non certifié → personne* **avant** les rôles (placée après, la clause serait oubliée au premier rôle ajouté) ; administrateur toujours ; permission `tournaments` seulement si le joueur est engagé dans un tournoi **vivant** (tout état sauf `FINISHED` — le besoin naît du tournoi et s'éteint avec lui) ; jamais public, et le cast n'y a pas droit (diffuser n'est pas joindre). Filtrage posé **à la sortie** (`visibleDiscordTag`, comme `visibleAvatarUrl`) : un écran ajouté demain n'a rien à afficher plutôt qu'à se souvenir d'une règle, et la question du tournoi n'est posée en base que quand elle peut changer la réponse. **Le tag et la certification sont deux faits, pas un** : le tag dit *comment* joindre (coordonnée, filtrée), la certification dit seulement *qu'il est joignable* (état, annoncé à tout lecteur — `canSeeDiscordVerification`), d'où l'affichage « Masqué ✅ ». Le second manquait au capitaine dont le tournoi exige « tous les Discord vérifiés » : il lisait un refus sans savoir qui de son roster devait encore certifier. **La preuve est celle de la connexion** — le même code à six chiffres, la même table, les mêmes deux bornes —, et elle se réduit à **un aller-retour OAuth** quand le compte porte déjà un `discord_id` : le dialogue le renvoie chez Discord (`intent=link`), qui retrouve la même identité et nomme le pseudo, que `linkOAuthIdentity` réécrit certifié (`REFRESHED`). **Jamais par le bot** : il ne résout un tag qu'en balayant les serveurs qu'il partage avec le joueur, et un compte venu par OAuth ou par un code demandé avec son identifiant numérique n'en partage souvent aucun — la recherche les parcourait tous, dépassait le délai, et le profil annonçait « bot non joignable » (un dépassement de délai se nomme désormais `BOT_RESOLVE_TIMEOUT`, distinct de l'injoignable). Se connecter par Discord **certifie donc le tag tout seul** : la route de connexion *consomme* le défi (`consumeDiscordChallenge`) au lieu de le vérifier, en relit le `handle` — le tag qui a servi à la résolution, **jamais celui que le client renvoie**, qu'aucune preuve ne couvre plus — et `createOrGetDiscordUser` l'écrit certifié. Un identifiant numérique n'est **pas** un tag (`normalizeDiscordHandle` le rejette) : la connexion l'accepte en repli, la certification publie un pseudo à l'arbitrage. On ne **déplace jamais une porte d'entrée** : un tag qui résout vers un autre compte Discord est refusé (`DISCORD_ID_MISMATCH`), jamais rattaché — et un Discord déjà certifié ailleurs bute sur `DISCORD_ALREADY_LINKED`, le `SELECT` donnant le refus lisible et l'index unique tranchant la course. **Toute modification du tag défait la certification** : `updateOwnProfile` pose le `CASE` **avant** l'affectation de `discord_pseudo` (MySQL évalue de gauche à droite, placé après il lirait la valeur neuve), en `<=>` parce que le tag peut être `NULL` des deux côtés. C'est aussi le geste d'annulation offert au joueur, d'où **aucune** route de décertification. **Un compte Discord rattaché possède son tag** (`lib/shared/discord-tag-lock.ts`) : le champ passe en lecture seule et **« Recertifier » disparaît** — le rattachement écrit déjà le pseudo que Discord nomme, certifié, si bien que rouvrir la saisie n'offrait qu'un moyen de perdre la certification d'une faute de frappe puis de la replacer à l'identique. Ce qui reste, c'est ce qui a encore un objet : « Certifier mon tag » tant que le tag enregistré ne l'est **pas** (tag saisi avant la règle, ou rattachement sans pseudo certifiable), « Enregistrer mon tag » quand il n'y en a aucun, et « Réessayer » quand l'état n'a pas pu être lu — les gestes sont sous le **rattachement**, jamais sous la présence d'un tag. Refus en **409 `DISCORD_TAG_LOCKED`** sur un tag *différent et non nul* (le formulaire renvoie le champ à chaque sauvegarde), et l'écriture le garde d'elle-même par un `CASE`, le `SELECT` ne donnant que le refus lisible. **Retirer son tag reste possible**, par un bouton « Retirer mon tag » qui remplace celui de certification — le champ ne se vidant plus à la main, la sortie que le serveur accepte n'existerait nulle part ailleurs. C'est le seul geste d'annulation de l'exposition, et le refuser enfermerait un compte né par Discord — tag certifié donc lisible de l'arbitrage, et détachement refusé en `LAST_CONNECTION` faute d'une autre porte. Au passage, **un champ absent du patch n'est plus un champ vidé** : `discordPseudo` manquant valait `null` donc un effacement, ce que le verrou aurait transformé en 409 sur tout compte rattaché. Pastille `public/badge-certifie.webp` par `components/discord-tag.tsx`, affichée **avec ou sans son tag** (le composant n'a qu'un seul chemin de rendu : son repli sortait d'abord, si bien qu'un joueur certifié dont le tag était filtré n'annonçait rien) ; les contacts d'un plateau se lisent **à la demande** (`GET /api/admin/tournaments/[id]/contacts`) et **jamais dans l'instantané**, qui est diffusé tel quel à tous les abonnés du flux — et ce panneau **se ferme avec le tournoi** (`tournamentGrantsContactAccess`), sans quoi il rendrait après la clôture ce que la fiche d'un joueur refuse. Voir `docs/features/DISCORD_VERIFICATION.md`.

**En-têtes de sécurité** (`next.config.ts`) : `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` et `X-Frame-Options: SAMEORIGIN` sur toutes les réponses. Pas de `Strict-Transport-Security` : le chiffrement se termine au reverse proxy, c'est à lui de l'annoncer — posé ici, il s'appliquerait aussi à un déploiement servi en clair (nginx le pose bien, vérifié sur la production). Et `poweredByHeader: false`, qui **retire** celui que Next pose seul : `X-Powered-By: Next.js` partait à chaque visiteur en production. Le taire ici plutôt que dans nginx n'est pas indifférent — la configuration du proxy n'est pas versionnée dans ce dépôt, elle est partagée avec un autre site, et elle ne suivrait pas un déploiement fait ailleurs.

**`Content-Security-Policy`** (`lib/shared/csp.ts` + `middleware.ts`) : posée **en application** (`CSP_MODE = "enforce"`) — elle refuse. L'objection qui la retenait — « Next injecte ses propres scripts en ligne, une politique écrite à l'aveugle casserait la page sans qu'aucun test ne le voie » — se scinde en deux, et les deux moitiés ont maintenant une réponse. Les scripts de Next se **nomment** : le middleware tire un nonce par requête, le pose en en-tête de **requête** (Next le lit et l'appose lui-même sur chacune de ses balises — 141 sur 142 à l'accueil, la dernière étant le JSON-LD, que le navigateur n'inspecte pas) et en en-tête de **réponse** (le navigateur sait alors lesquelles sont nommées). Et l'aveuglement, c'est le mode qui le lève : le navigateur signale ce qu'il aurait refusé, `POST /api/csp-report` le journalise **une fois par cause et par heure** (`lib/server/csp-reports.ts` : ni URL complète, ni extrait de script, ni stockage — l'application sœur a déjà produit un log de 235 Mo faute de dédoublonnage). Le basculement s'est fait d'un mot (`CSP_MODE`), une fois l'obstacle levé — et **la façon dont il l'a été est ce qu'il faut retenir**.

Une page prérendue ne peut pas porter de nonce : un HTML bâti à la compilation est le même pour tous, or un nonce dans la politique fait **ignorer** `'unsafe-inline'`, si bien que ses scripts en ligne étaient refusés en application. La liste de ces pages, longtemps écrite « cinq routes » ici et dans `csp.ts`, était **fausse** : elle se lisait sur le résumé de `next build`, elle se lit dans `.next/prerender-manifest.json`. Il y en avait **trois**, dont une inoffensive — `/connexion` (8 scripts en ligne, 0 nommé), `/_not-found` (7, 0), et `/partenaires` (8, 0) qui répond `308`, donc dont le corps n'est jamais rendu. `/regles/[slug]` s'affiche `●` mais n'écrit aucun HTML et n'y figure pas : elle est rendue à la demande (deux requêtes en production rendent deux nonces différents), l'arbitrage qu'on croyait devoir trancher à son sujet n'a jamais existé ; et `/opengraph-image` rend un PNG.

La levée ne s'est donc **pas** faite route par route mais à la cause : le HTML de chaque page dépend d'un en-tête de requête, Next ne compte pas cette lecture comme une dépendance dynamique, et `app/layout.tsx` la lui **déclare** d'un `await headers()`. Une liste de `force-dynamic` aurait dérivé comme la précédente ; une dépendance à la racine couvre la page ajoutée demain. Il ne reste plus **aucune** page prérendue, `/opengraph-image` exceptée — et tant mieux, la fabriquer par requête coûterait cher. Coût mesuré : ~4,5 ms de rendu serveur par page (médiane 8,3 ms contre 3,8 ms pour une page encore statique, même compilation, à chaud), sans accès base, à paquet client inchangé ; ce qui se perd est la mise en cache du **document**, qui passe sous `private, no-cache, no-store` — déjà le régime de toutes les autres pages, l'en-tête de session s'y trouvant. Vérifié sur la compilation de production, session réelle comprise : **16 pages à 100 % de nonces** (404 et `/connexion` compris), flux SSE ouvert, formulaire de connexion soumis, et **zéro violation** au collecteur — dont on a prouvé qu'il journalisait bien, en lui envoyant un rapport témoin.

**Si une page casse après un ajout**, lire `/api/csp-report` avant de toucher à la politique : en application, un refus est immédiat et visible, c'est le seul avantage de ce mode. Repasser en `Report-Only` reste un mot, le temps d'un diagnostic. Le second obstacle, l'avatar d'un compte Google servi par `lh3.googleusercontent.com`, est levé : la photo est copiée chez nous à la connexion (voir « Avatars » ci-dessous) et `img-src` est redevenue `'self' data: blob:`, donc le détecteur de toute image tierce réintroduite.

**Avatars — jamais une origine étrangère** (`lib/shared/avatar.ts` + `lib/server/user-avatar-import.ts`) : `createOrGetGoogleUser` rangeait l'URL de `picture` telle quelle et `UserAvatar` la rendait en `unoptimized`, si bien que chaque page portant cet avatar faisait partir une requête du navigateur du **visiteur** vers Google — l'IP de qui regarde, pas celle du titulaire, et à chaque vue ; le `referrerPolicy="no-referrer"` déjà posé ne couvrait que le référent. La photo est désormais **copiée** à la connexion, par les gardes du relais partenaires (`lib/shared/remote-image.ts` + `lib/server/remote-image-fetch.ts`, extraits pour être partagés) puis par le traitement d'un téléversement ordinaire (`storeImageBuffer`) : même dossier, même service, même optimisation qu'un avatar choisi sur `/profil`. **Copier plutôt que relayer** — un logo partenaire est modifiable à tout moment et doit suivre, une photo de profil est acquise à la connexion ; ils sont six quand les comptes sont des milliers ; et un avatar est soumis à un réglage de visibilité qu'une route publique aurait dû réimplémenter. La garantie est posée à la **sortie**, dans `visibleAvatarUrl` : une URL qui n'est pas un fichier à nous rend `null`, et l'écran retombe sur la pastille à initiale — totale par construction, là où filtrer au rendu dépendrait du prochain écran écrit. L'import ne remplace **jamais** un avatar téléversé (`shouldImportGoogleAvatar`), ce qui referme au passage un défaut préexistant : l'ancien `avatar_url = COALESCE(?, avatar_url)` écrasait à chaque connexion Google la photo choisie sur `/profil`. Contrepartie assumée : une photo changée **côté Google** ne se propage plus. Les comptes d'avant se réparent à leur prochaine connexion, ou d'un coup avec `npm run backfill:avatars`. Voir `docs/features/USER_AVATAR_IMPORT.md`.

Auth enforcement: `app/(secured)/layout.tsx` lit la session côté serveur et, **sans session, ne redirige pas** : il rend une carte « Connexion requise » (`_shared/AuthGate.tsx`) en `200`, sans rendre ses enfants — rien du contenu protégé n'atteint la réponse. Deux raisons, l'une pour les humains et l'autre pour les robots : la redirection perdait la destination (elle ne portait aucun `?redirect=`, que `/connexion` sait pourtant lire), et un `307` n'a pas de `<head>`, donc aucun aperçu de lien partagé n'était possible sur une fiche de tournoi. Les métadonnées du segment demandé sont, elles, bien émises — Next résout `generateMetadata` de tout l'arbre correspondant à l'URL, indépendamment de ce qu'une mise en page choisit de rendre. Voir `docs/features/SHARE_METADATA.md`.

### Database (`lib/server/database.ts`)
Direct MySQL2 pool. Le schéma est joué automatiquement à la première requête. Tables : `bg_users`, `bg_teams`, `bg_team_members`, `bg_tournaments`, `bg_tournament_registrations`, `bg_matches`, `bg_user_sessions`, et une par moteur ou fonctionnalité (classements, phases, notifications envoyées, vitrine).

**Le fichier décrit le schéma tel qu'il est, pas l'histoire de la façon dont on y est arrivé.** Soixante-trois `ALTER TABLE` s'y étaient empilés, chacun dans un `catch {}` vide pour retomber en silence sur une base qui l'avait déjà subi : on ne pouvait plus lire la définition d'une table sans parcourir mille lignes, l'ordre des colonnes racontait la chronologie des fonctionnalités plutôt que la structure de l'objet, et chaque démarrage rejouait des conversions d'ENUM et des backfills sans objet depuis des mois — certains en balayage de table complète. Ils sont désormais repliés dans les `CREATE TABLE`, groupés par domaine.

**La contrepartie est à connaître avant de toucher au fichier** : sur une base qui existe déjà, `CREATE TABLE IF NOT EXISTS` ne fait **rien** — il ne rattrape ni une colonne ni un index. Le repli n'est sans danger que parce que la production porte déjà le schéma complet ; une base restée à une version antérieure doit être migrée à la main. **La règle pour la suite est donc inchangée** : un changement de schéma s'écrit à **deux** endroits — dans le `CREATE TABLE` (bases neuves) *et* en `ALTER TABLE` tolérant dans la section « Migrations » (bases qui tournent) —, cette seconde entrée pouvant être retirée une fois qu'on la sait jouée partout. Seuls deux **rattrapages permanents** subsistent, dont la cause peut se reproduire : l'invitation Discord périmée du pied de page et le logo d'une entrée solo qui republierait un avatar masqué.

**`bg_users.email` n'existe plus.** La colonne n'avait plus aucun lecteur (le scope `email` a disparu de la demande faite à Google, un compte ne se revendique plus par son adresse) et gardait pourtant les adresses collectées avant la règle : garder une donnée que plus personne ne lit n'est pas de la prudence, c'est une fuite en attente. Le `DROP COLUMN` est l'un des trois chemins d'`ALTER` que le fichier porte encore, avec le retrait de `bg_recruitment_ads.contact_email` et la liste `RECENT_SCHEMA_CHANGES` (les changements trop récents pour qu'on sache la production passée dessus — des instructions entières, pour que la règle couvre aussi un `ENUM` élargi ou un index posé) ; il est **irréversible** et s'applique au prochain redémarrage — un retour en arrière de la version applicative après ce déploiement casserait les lectures de session. `AuthUser.email`, l'anonymisation, l'export RGPD et le jeu de test l'ont suivi. Voir `docs/DATABASE_SCHEMA.md`.

### Tournament Engine (`lib/server/tournaments-service.ts`)
Supports single/double elimination, Swiss round and Survival formats. Key concepts:
- **Formats:** `SINGLE`, `DOUBLE`, `SWISS`, `SURVIVAL` (single group, seed by site ranking, adjacent pairing, coupes des 2 derniers — `survivalRoundsBeforeFirstCut` manches avant la première, puis toutes les `survivalRoundsPerCut` — jusqu'à une championne ; odd field → round-1 barrage between the bottom two so no byes are ever handed out — see `docs/features/SURVIVAL_MODE.md`). Survival logic lives in `lib/shared/survival.ts` (pure) + `lib/server/tournaments/survival.ts` (orchestration). `reconcileSurvival` **rejoue** tout le tournoi depuis l'historique des matchs (`replaySurvival`) : victoires, défaites, éliminations et rangs sont dérivés, jamais accumulés — une correction de score défait donc la coupe qu'elle avait provoquée, et le round suivant est réapparié tant qu'il n'est pas entamé. Seuls les abandons sont conservés en entrée. Le seeding utilise le classement partagé du site (`loadEntrantsBySiteRanking`), commun au leaderboard de la landing.
- **Format `MULTI` (multi-phases)** : suite ordonnée de 2 à 8 phases, chacune dans son propre format (`SWISS`/`SURVIVAL`/`SINGLE`/`DOUBLE`), ne transmettant que ses qualifiées à la suivante — la dernière désigne la championne. La qualification se règle par phase, **en nombre fixe** (l'effectif réel étant déjà sous la cible, la phase est **sautée** : c'est le cas du tournoi sous-rempli) ou **en pourcentage** (la cible s'adapte à l'effectif). Une phase `SINGLE` intermédiaire arrondit sa cible à la puissance de deux inférieure et joue un bracket tronqué ; `DOUBLE` n'est autorisé qu'en phase finale. Le plan restant est **re-résolu à chaque fin de phase** avec le nombre réel de qualifiées, si bien qu'un abandon peut faire sauter une phase ultérieure. Logique pure dans `lib/shared/tournament-phases.ts`, orchestration dans `lib/server/tournaments/phases.ts` (`initializeMultiTournament` → `startPhase` → `reconcilePhases` → `finalizeMultiTournament`). Comme les trois modes à classement, `reconcilePhases` **relit un tournoi clos** — corriger la finale doit se voir au palmarès ; le mode en sortait par **deux** gardes et non une (l'état du tournoi *et* celui de la phase courante, close elle aussi), si bien qu'il a fallu accepter l'état terminal aux deux, et **seulement lui** : sur un `FINISHED`, la phase courante doit être `FINISHED`. Le classement de cette phase est réécrit et la finalisation rejouée, mais rien n'est reposé — ni redatage de la clôture de phase, ni re-résolution du plan restant, ni démarrage de phase. Relire la seule phase courante suffit : `match-lock` ne laisse corrigible que la dernière manche de la dernière phase. Les matchs portent un `phase_id` (**0** = tournoi sans phases, ce qui laisse tous les formats existants inchangés). Voir `docs/features/MULTI_PHASE_TOURNAMENTS.md`.
- **Mode `BG_SURVIE` (« BlueGenji Survie »)** : capital d'**endurance** (9 par défaut, réglable) — +1 par map gagnée, −1 par map perdue (un 3-0 déplace donc trois points, un 3-2 un seul : le barème n'est **pas** par match), **élimination immédiate à 0**. Un **forfait** vaut le score plein du format du tournoi (FT3 → 3-0, `forfeitMapCount`), et non un match blanc : les colonnes de score étant `NULL` sur un forfait arbitré, le barème se dérive du format. L'abandon se déclare depuis le classement d'`EnduranceView`, par un représentant de l'engagé ou par `can(user, "tournaments")`. Classement relu avant chaque manche (endurance puis **ordre du classement précédent**, pas le seed), appariement par couples adjacents, la mieux classée à gauche ; effectif impair → la dernière ne joue pas (aucune victoire d'office). La phase qualificative s'arrête à 8 équipes — ou, si le tournoi fixe un **plafond de manches** (`endurance_max_rounds`, `NULL` = aucun, comportement d'origine), à la manche dite : les 8 premières du classement sont alors qualifiées, **toutes les autres sortent**, capital en poche. Sous plafond, une équipe qui ne peut plus **mathématiquement** rejoindre le plateau est écartée sans attendre — critère volontairement conservateur (le **plancher** de `playoffSize` adversaires doit dépasser strictement son **plafond**, plafond de maps tiré du format de match ; en **saisie libre**, rien n'est acquis et personne n'est jamais écarté d'avance), et **abandonné** s'il laisserait un effectif impair *à qui il reste des manches* — un effectif impair fait chômer une équipe, et on ne prive pas une équipe en course pour sortir des condamnées qui le resteront la manche suivante. D'où un statut à part, `OUT_OF_CONTENTION` (« Hors course ») : l'écartée **garde son capital**, et « Éliminée » à côté de neuf points serait un contresens. Tout cela vit dans `replayEndurance` (`enduranceEliminationCut`), donc se défait avec une correction de score ou le retrait du plafond ; `reconcileEndurance` n'a **aucune branche** pour le plafond (le rejeu ayant ramené l'effectif à la cible, la bascule habituelle suffit), seul `generateEnduranceRound` garde un `roundLimitReached` pour qu'aucun chemin ne pose une manche de trop. Puis arbre imposé **8v4 / 6v2 / 1v5 / 3v7** + petite finale (manches numérotées à partir de 1000). Classement de départ = **ordre de seeding fixé à la main**. `reconcileEndurance` ne décide **rien au milieu d'une manche** : la fin de la manche courante (`roundIsComplete`) conditionne aussi bien l'appariement de la suivante que la bascule en play-offs — un seul score faisant tomber l'effectif actif sur la cible lançait sinon l'arbre en laissant les autres rencontres de la manche ouvertes à jamais. Une manche **périmée** (posée, jamais jouée, aux appariements réécrits par une correction en amont) est défaite puis *retombe sur cette même décision* : la défaire et sortir laissait le tournoi sans manche et sans arbre dès que la correction achevait la qualification. **L'arbre final se relit de la même façon** (`repairPlayoffBracket`) : `finalizePlayoffsIfDone` ne sait que *poser* le tour suivant, si bien qu'une fois les demies créées, corriger le vainqueur d'un quart n'en changeait plus les participantes — elles continuaient d'annoncer une équipe qui venait de perdre. Les tours de play-off sont donc parcourus du premier au dernier, chacun confronté à ce qui le décrit (le **classement** pour le premier via `planPlayoffFirstRound`, les **vainqueurs du tour amont** pour les suivants via `planNextPlayoffRound`) ; le premier tour périmé est réécrit — **sur place** quand le plan garde la même forme, un identifiant de match étant une adresse publique (lien profond, diffusion, horaire) — et tout ce qui en descendait est supprimé, faute de base. Un tour portant la moindre saisie n'est **jamais** réécrit. Poser l'arbre et le réparer passent par les mêmes fonctions pures et le même écrivain (`writePlayoffRound`) : une réparation ne peut pas produire un autre tableau qu'un lancement. Logique pure `lib/shared/bg-survie.ts`, orchestration `lib/server/tournaments/bg-survie.ts`, table `bg_endurance_standings`, rejeu complet comme la Survie. **Deux forfaits à ne pas confondre** : sur **une manche** (arbitrage, depuis le dialogue de score — l'équipe reste en lice, la manche est comptée au score plein du format par `forfeitMapCount`, désormais **écrit en base** par `adminResolveMatch` et non laissé à `NULL`) et sur **tout le reste du tournoi** (`POST /api/tournaments/[id]/forfeit` — capital à 0, plus jamais appariée ; refusé hors `RUNNING` comme en Survie et en Ronde suisse, et le contrôle d'état passe **avant** celui des play-offs — un tournoi clos faute de qualifiées garde `endurance_playoffs_started` à 0, si bien que l'abandon s'écrivait sur une archive). Le classement se lit aussi **manche par manche** (`replayEnduranceDetailed`, jamais stocké) : une équipe retirée y porte « FF » en rouge sur ses manches restantes, à la place d'un capital. Distinct de `SURVIVAL`, qui reste inchangé. Voir `docs/features/BG_SURVIE_MODE.md`.
- **Pénalités d'endurance** (`lib/shared/endurance-penalty.ts` pur + `applyEndurancePenalty` / `liftEndurancePenalty`) : l'arbitrage retire des points de capital sans passer par un score de match (retard, joueur non éligible, conduite antisportive). La sanction est une **entrée du rejeu**, au même titre qu'un abandon, et non un cumul au classement — celui-ci est réécrit à chaque entretien, un total qui y vivrait serait effacé au premier score corrigé. D'où sa propre table (`bg_endurance_penalties`), une ligne par sanction, portant la **manche courante** : le rejeu l'applique après les matchs de cette manche et **avant** les abandons, si bien qu'une sanction qui vide le capital **élimine** (règle du mode) mais qu'un abandon déclaré la même manche reste ce qui s'écrit — la bascule `eliminatedThisRound` existante s'en charge. Corollaire : **une pénalité n'ajoute jamais**, on la **retire** (`DELETE .../penalties/[penaltyId]`), et le rejeu défait alors la sanction *et* ce qu'elle avait entraîné (élimination, coupe sous plafond, appariement de la manche suivante tant qu'elle n'est pas entamée) — une seconde ligne de sens inverse ne saurait pas faire cela. Trois fenêtres, jamais une seule : **tournoi en cours** (`TOURNAMENT_NOT_RUNNING` — la réconciliation rejouant désormais aussi les tournois clos, une sanction tardive ne serait pas ignorée mais réécrirait un palmarès **déjà publié**, sans qu'aucune manche ne puisse plus y répondre ; le cas est atteignable, un tournoi clos faute de qualifiées garde `endurance_playoffs_started` à 0) ; poser **comme** retirer refusés dès les play-offs lancés, pour deux raisons distinctes (poser n'aurait aucun effet mais figurerait au tableau comme si, retirer en aurait un et pourrait ramener « en lice » une équipe que l'arbre est déjà tiré sans elle) ; et le **retrait seul** verrouillé dès qu'une manche postérieure porte une saisie (`ENDURANCE_ROUND_ALREADY_PLAYED` → 409) — c'est `match-lock` transposé, et le retrait est le seul geste du mode qui remonte le temps : sans lui, lever une sanction de la manche 2 à la manche 7 rendrait son capital **intact** à une équipe qui n'a pas joué les quatre manches écoulées, le moteur ne réappariant que la manche courante. Le prédicat « ce match porte une saisie » est écrit une seule fois (`HAS_SCORE_INPUT_SQL`) et sert aussi à la borne `EndurancePenaltyRow.removable`, que l'interface reçoit pour afficher « 🔒 Figée » plutôt qu'un bouton voué au refus. Motif **obligatoire** (une sanction publique qui change un classement sera contestée) et auteur nommé, `NULL` si le compte est supprimé : le compte s'efface, la sanction reste due. `checkEndurancePenalty` est l'unique implémentation, partagée par le dialogue et la route. Affichage à trois endroits, jamais concurrents : `−N` ambre à côté du capital (cumul de la **baisse réelle** du capital — une sanction visant une sortie n'ampute rien, et une pénalité de 5 sur une équipe à 2 points n'en retire que deux), journal des sanctions visible de **tous** sous le classement (seul « Retirer » est réservé à l'arbitrage), et **soulignement ambre** sur la case de la manche dans le tableau manche par manche — la case garde son ton, le capital est ce qu'elle dit, la pénalité explique seulement pourquoi il a bougé. Journal Discord : deux évènements au **journal** (`endurance_penalty`, `endurance_penalty_lifted`) — c'est l'arbitre qui vient de les poser, rien à lui renvoyer — et les **deux seules entrées de la file qui portent leur substance** plutôt qu'un renvoi, la ligne d'une pénalité retirée n'existant plus à la résolution, qui suit le commit. Voir `docs/features/ENDURANCE_PENALTIES.md`.
- **Vue du mode BG Survie — volets de manche et vrai arbre** (`app/(secured)/tournois/[id]/_lib/endurance-sections.ts` pur + `_components/EnduranceRoundPanels.tsx`) : la vue empilait **toutes** ses rencontres en une colonne — dix manches à seize équipes font quatre-vingts cartes à la file, où rien ne dit où commence la manche courante —, et rendait les play-offs de la même façon : on lisait les rencontres d'un tour sans jamais voir **qui affronte qui au tour suivant**, une élimination directe sans son arbre. Une manche par **volet** désormais (`BoardPanel`, le chrome extrait de `BracketSections` — deux copies auraient divergé au premier réglage ; il apporte au passage l'anneau de focus clavier qui manquait aux tableaux à élimination), cartes rangées en `flex-wrap` plutôt qu'en colonne (elles ont une largeur fixe, elles se répartissent seules), et **les play-offs passent par `BracketSections`**, le composant de l'élimination simple, sans variante. Deux points à connaître. La **petite finale** vit dans la même manche que la finale : alignée dans la dernière colonne de l'arbre elle serait nommée « Finale 2 », d'où un second `BracketSections` de type `THIRD_PLACE`, comme le fait déjà la page pour les tableaux à élimination. Et le mode ne renseigne **aucun** `next_winner_match_id` (le moteur crée le tour suivant une fois le précédent complet) : les liens de l'arbre sont **dérivés** de la règle d'appariement du moteur par `endurancePlayoffLinks` (le vainqueur du i-ème match joue le (i/2)-ème du tour suivant), et `BracketTree` les prend par un `resolveNextMatchId` optionnel dont le repli est le comportement d'origine. Ce lien ne sert **qu'au dessin** : le verrou de score se décide sur le numéro de manche (`dependentMatches`), jamais sur un lien de bracket, et rien de ce qui est calculé là ne remonte au serveur. Le mode pose aussi ses tours **un à la fois**, là où `BracketSections` a été écrit pour des tableaux qui naissent entiers : d'où un `plannedRounds` (calculé par `endurancePlayoffRoundCount` depuis l'effectif du premier tour) qui nomme les stades sur le tableau **complet** — sans lui, les quarts s'appelaient « Finale » tant qu'ils étaient seuls posés — et une **clé de section devenue le numéro de son premier tour** plutôt que son titre : le titre change quand la section grandit (« Finale » → « Phase finale »), `openKeys` n'est écrit qu'au montage, et le volet se refermait donc tout seul au moment précis où l'arbre avançait. Les manches restent affichées **sous** l'arbre une fois les play-offs lancés — l'ancienne vue les remplaçait purement, et le parcours d'une équipe disparaissait au moment où il devenait intéressant. Le volet ouvert d'office **suit la manche courante** au fil du flux (un état figé au montage laisserait le lecteur sur une manche close), sans jamais rouvrir ce qu'il a replié à la main — et `BracketSections` suit désormais la même règle, son état étant lui aussi figé au montage : invisible sur un tableau à élimination, dont le découpage est acquis dès la génération, mais pas sur un arbre qui se réorganise (au-delà de trois tours, la « phase finale » glisse d'une section à l'autre, et celle qui recevait le tour vivant naissait repliée). `EnduranceView` reçoit enfin les mêmes props que ses voisines (`canReport`, `drafts`, `format`…) au lieu d'un `renderMatch` : la page ne connaît plus `MatchRow`. Voir `docs/features/ENDURANCE_ROUND_PANELS.md`.
- **Tournoi individuel** (`bg_tournaments.participant_type = 'SOLO'`) : les joueurs s'inscrivent eux-mêmes, sans équipe. Le moteur ne connaît que des **engagés** identifiés par un `team_id` ; un joueur reçoit donc une **entrée solo** (ligne `bg_teams` avec `solo_user_id`, sans membre, comme une fantôme), créée à sa première inscription. Tous les formats fonctionnent inchangés. L'entrée solo n'est pas une équipe : exclue de `/equipes`, du classement du site et du compteur d'équipes ; sa fiche renvoie vers `/joueurs/[id]`. Résolution unique de l'engagé : `resolveUserEntrantTeamId` (`lib/server/tournaments/registration.ts`), à utiliser pour l'inscription, le report de score et l'abandon. Vocabulaire pur dans `lib/shared/participants.ts`, service dans `lib/server/solo-entries-service.ts`. Voir `docs/features/SOLO_TOURNAMENTS.md`.
- **Format de match** (`lib/shared/match-format.ts`, pur) : chaque tournoi peut fixer un **BO** (best of, nombre impair de manches jouées) ou un **FT** (first to, manches à gagner). Deux colonnes `bg_tournaments.match_format_type` / `match_format_value` (NULL = score libre, comportement des tournois antérieurs). `checkMatchScores` est l'unique implémentation, partagée : l'interface borne les champs et désactive « Gagnant », le serveur refuse en 400 (`SCORE_EXCEEDS_MATCH_FORMAT`, `SCORE_BELOW_MATCH_FORMAT`, `DRAW_NOT_ALLOWED`) dans `reportMatchScore` et dans l'arbitrage. Une sauvegarde intermédiaire ne contrôle que le plafond ; une saisie qui désigne un vainqueur exige un **résultat final**. Le réglage vaut pour **tout** le tournoi, phases comprises — sauf en BG Survie, seul mode à en jouer deux (ci-dessous). Voir `docs/features/MATCH_FORMAT.md`.
- **Matchs nuls et plafond de maps** (`lib/shared/match-format.ts` + `tournamentMatchFormat` dans `lib/shared/bg-survie.ts`) : « BO5 » et « FT3 » désignaient **le même objet** — plafond toujours à `objectif × 2 − 1`, vainqueur toujours exigé —, si bien qu'aucun réglage ne pouvait dire « premier à trois, cinq maps au maximum, et tant pis si personne n'y arrive ». Or Overwatch et Marvel Rivals connaissent la **map nulle**, et la qualification BG Survie se joue en BO5 *sans tiebreaker*. Deux champs facultatifs les séparent, sans rien changer aux tournois qui ne les posent pas : `maxMaps` (plafond de maps **décisives**, c.-à-d. la somme des deux scores — une map nulle ne figure dans aucun, elle allonge la rencontre sans consommer le plafond ; « 5 maps » veut donc dire « 5 maps décisives », seule lecture que les colonnes permettent) et `drawsAllowed` (n'importe quel score dans le plafond clôt la rencontre : 2-2, 2-1, jusqu'à 0-0). **Les deux vont ensemble** : un plafond abaissé *est* la fenêtre du nul, et posé sans elle il ne retire que des issues — un FT3 plafonné à 4 maps refuse `3-2` (somme 5) *comme* `2-2` (pas de vainqueur), si bien qu'une série arrivée à 2-2 n'a plus aucun score enregistrable et bloque son plateau ; d'où `matchMaxMapsNeedsDraws` (refus `MATCH_FORMAT_MAX_MAPS_REQUIRES_DRAWS`), un champ qui ne s'affiche qu'une fois la case cochée, et un `withoutDraws` qui **rend le plafond naturel** au format qu'il ferme — sans quoi le repli de l'arbre final fabriquait l'impasse lui-même. Pas de branche `DRAW_NOT_ALLOWED` sur un format qui exige un vainqueur, et ce n'est pas un oubli : une égalité **sous** l'objectif est d'abord un score incomplet (le refus renvoie au bon geste), une égalité **à** l'objectif dépasse déjà le plafond — le code ne subsiste que pour la **saisie libre**, où il n'y a aucun objectif à opposer. **BG Survie joue deux formats** : la qualification (égalités éventuellement ouvertes) et l'arbre final (`endurance_playoff_format_*`, **jamais** d'égalité — une élimination directe doit savoir qui joue le tour suivant ; sans réglage propre, elle rejoue celui du tournoi *égalités fermées*, `withoutDraws`). La règle est écrite **une fois**, `tournamentMatchFormat`, et appelée des deux côtés — `loadTournamentMatchFormat` côté serveur, le contexte React `useMatchFormat(match)` côté interface : deux copies auraient divergé au premier réglage, et la divergence se serait vue en 400 sur un formulaire qui s'annonçait valide. `PLAYOFF_ROUND_OFFSET` a rejoint le module pur pour la même raison (moteur, vue, résolution du format). Un nul s'écrit `COMPLETED` + `winner_team_id`/`loser_team_id` à `NULL` + deux scores égaux, et se **reconnaît** à ces trois traits conjoints : clos sans vainqueur *ni* score, c'est une ligne abîmée, elle reste dehors partout. `matchWinnerSide` est l'unique dérivation du vainqueur, partagée par les trois chemins qui tranchent un match (arbitrage, accord des deux engagés, expiration du délai) — ils en avaient chacun une, avec deux règles différentes pour l'égalité (`>` / `>=`), sans conséquence tant qu'aucun nul n'était enregistrable. Le **capital d'endurance** n'a besoin d'aucune règle nouvelle (barème map par map : un 2-2 déplace deux points dans chaque sens, donc rien au barème ±1), la coupe mathématique non plus (le meilleur et le pire cas d'une équipe sont inchangés) ; le classement gagne une colonne `draws`, affichée seulement si le tournoi en a produit un. Le **classement du site** compte le nul : `playedMatchSql` l'admet explicitement, et `ratingDrawTransfer` transfère `K × (E − 0,5)` du favori vers l'outsider — 13 points pour une 500 qui tient tête à une 900, contre 29 si elle l'avait battue. Les **fiches** portent `StatsMatch.outcome` (`WIN`/`LOSS`/`DRAW`) et non plus un booléen, sans quoi un nul comptait pour une défaite et brisait les séries ; il rompt les deux séries, reste au dénominateur du ratio, et s'affiche « **N** » sur les pastilles de forme (« D » y désigne déjà la défaite). Enfin, **« jouée » ne se lit plus sur le vainqueur** : cinq écrans en jugeaient par `winnerTeamId !== null`, si bien qu'un nul passait pour une rencontre à venir — manche complète annoncée « 5/6 jouées » et jamais refermée, volet ouvert sur une manche close, formulaire de report rouvert sur un match fini, « ton prochain match » sur un match joué, et surtout `isScoreEditLocked` qui rouvrait l'édition là où le serveur la refuse en 409 (le bouton menait à un mur). `lib/shared/match-outcome.ts` porte les deux prédicats — `isMatchPlayed` (le **statut** fait foi) et `isMatchDrawn` (terminé, sans vainqueur, pas par forfait, deux équipes réelles) —, et `MatchScoreState` gagne un champ `decided` : ni « a un vainqueur » (un nul en est un sans), ni « porte un score » (l'arbitrage note un 1-1 en cours de rencontre). Voir `docs/features/MATCH_DRAWS.md`.
- **Conditions d'inscription** (`lib/shared/registration-filters.ts` pur + `lib/server/tournaments/registration-eligibility.ts`) : un tournoi s'annonçait ouvert à toute équipe existante, si bien que deux refus tombaient toujours le jour du coup d'envoi — l'équipe de deux joueurs sur un plateau 5v5, et celle que l'organisation ne peut joindre. Les deux se lisent sur le roster **avant** l'inscription : ce sont donc des conditions du tournoi. Trois réglages, `registration_discord_requirement` (`NONE` / `ANY_PLAYER` — défaut — / `ALL_PLAYERS`, sur le tag **certifié**, jamais sur une chaîne saisie), `registration_blizzard_requirement` (mêmes trois valeurs, `NONE` par défaut) et `registration_min_players` (5 par défaut, `1` = aucune exigence) ; colonnes `NOT NULL DEFAULT`, donc un tournoi d'avant en hérite. Les deux exigences de compte partagent un seul type (`PlayerRequirement`) et une seule mécanique (`checkPlayerRequirement`) : elles posent la même question, deux énumérations jumelles auraient divergé — à commencer par la liste déroulante qu'elles remplissent toutes les deux. **Ce qu'elles ne sont pas, l'une et l'autre** : un tag Discord est une **coordonnée** (joindre une équipe), un compte Battle.net rattaché une **attestation de compte de jeu** — d'où une lecture sur `bg_users.blizzard_sub` et **jamais** sur `overwatch_battletag`, chaîne libre où l'on écrit le tag de n'importe qui (même écart qu'entre `discord_verified_at` et `discord_pseudo`). Le défaut `NONE` de la condition Blizzard n'est pas une prudence de migration : la moitié du site joue à Marvel Rivals, où un compte Battle.net ne veut rien dire, et l'exiger par défaut fermerait des tournois sans raison. Trois portées à ne pas confondre : les **équipes fantômes** n'y sont pas soumises — le contrôle vit dans `registerCurrentUserTeam` et **jamais** dans le tronc commun `registerTeam`, seul endroit du moteur où la distinction se lit sans rien deviner ; une inscription **déjà enregistrée** n'est jamais relue (les conditions se jugent à l'écriture, comme `maxTeams`) ; et l'**effectif minimal ne s'applique pas en individuel**, où un engagé est une personne — le défaut à 5 y interdirait tout, sur un réglage que le formulaire ne montre même pas. Cinq refus distincts en **409** (`TEAM_TOO_FEW_PLAYERS`, `TEAM_NEEDS_VERIFIED_DISCORD`, `TEAM_NEEDS_ALL_VERIFIED_DISCORD`, `TEAM_NEEDS_LINKED_BLIZZARD`, `TEAM_NEEDS_ALL_LINKED_BLIZZARD`) : la saisie est bonne, c'est l'état de l'équipe qui ne convient pas, et chacun nomme le geste qui le lève. La liste est **énumérée dans le module pur** (`REGISTRATION_FILTER_ERRORS`, dont le type dérive) et la route la teste par `isRegistrationFilterError` : elle la recopiait, si bien qu'un refus ajouté d'un côté et pas de l'autre serait ressorti en **500** sur un cas parfaitement prévu. L'ordre des contrôles va du plus urgent au moins urgent — effectif (se corrige en recrutant), Discord (sans lui l'arbitrage ne joint personne), Blizzard (éligibilité au jeu seulement). `checkRegistrationFilters` est l'unique implémentation, sous deux habillages qui partagent la même lecture de roster (`checkEntrantEligibility`) : l'une **lève** (elle protège une transaction), l'autre **rend le refus** et ferme le bouton depuis `getTournamentViewerContext` — un bouton qui mène à un 409 est un bouton qui ment. Le motif voyage (`TournamentViewerContext.registrationBlock`) et `registerBlockedNotice` met à la place du bouton la phrase qui nomme le geste ; la lecture n'a lieu que lorsqu'elle peut changer la réponse (inscriptions ouvertes, engagé identifié, pas déjà inscrit, qualité pour engager), et reste **sur la connexion de l'appelant**, verrou du tournoi en main. Éditables après publication (`RESTRICTED_FIELDS`) : un tournoi annoncé où personne ne peut s'inscrire doit pouvoir être ouvert sans être recréé. Voir `docs/features/REGISTRATION_FILTERS.md`.
- **States:** `UPCOMING → REGISTRATION → RUNNING → FINISHED`
- **Tournoi sans adversaires** : un tournoi qui atteint son coup d'envoi avec **0 ou 1 engagée** ne passe pas « en cours » — il est clos sur-le-champ (l'unique engagée, s'il y en a une, est déclarée première). `finalizeUnderfilledTournament` (`lib/server/tournaments/finalization.ts`) est appelée par `syncTournamentState` **avant toute initialisation de format**, sur l'état *calculé* (`RUNNING`) et non sur la seule bascule depuis les inscriptions — un tournoi repasse par `UPCOMING` entre la clôture des inscriptions et l'heure de début, et un tournoi déjà `RUNNING` doit être rattrapé pareillement. Sans cette règle, chaque format doit connaître le cas dégénéré, et un plateau **sans aucune** engagée reste « en cours » à jamais en Suisse comme en BG Survie (leur réconciliation abandonne sur un classement vide) : c'est la fin des matchs qui clôt un tournoi, et il n'y en a aucun. Voir `docs/features/UNDERFILLED_TOURNAMENTS.md`.
- **Bracket positions:** `UPPER`, `LOWER`, `GRAND` finals
- **Match status:** `PENDING → READY → AWAITING_CONFIRMATION → COMPLETED`
- **Verrouillage de l'édition d'un score** (`lib/shared/match-lock.ts`, phase-aware : en `MULTI`, la règle interne est celle du format **de la phase**, et toute phase ultérieure verrouille les précédentes) : un score n'est plus modifiable — **y compris par un admin** — dès que la manche suivante porte la moindre saisie (un score même nul, un vainqueur, un forfait, ou un report en attente de confirmation). Les matchs dépendants suivent le format : liens `next_winner_match_id` / `next_loser_match_id` en élimination, tous les rounds ultérieurs en survie, en ronde suisse **et en BlueGenji Survie** (leurs appariements sont recalculés depuis le classement, ou depuis les vainqueurs du tour amont en play-off d'endurance — aucun de ces formats ne renseigne les liens de bracket, si bien que `BG_SURVIE` absent de cette liste côté serveur n'opposait **aucun** verrou là où l'interface masquait pourtant le bouton). Le module est pur et partagé : le serveur l'applique dans `checkDownstreamMatchesHaveNoScores` (`lib/server/tournaments/admin.ts`, erreur `CANNOT_MODIFY_COMPLETED_DEPENDENT_MATCHES` → 409) et l'interface masque le bouton « Éditer le score » au profit d'un indicateur « 🔒 Score verrouillé ». Les byes et matchs fantômes sont ignorés : leur score (1-0, 0-0) est posé par le moteur, pas saisi.
- **Double forfait** (`lib/shared/double-forfeit.ts` pur + `lib/server/tournaments/bracket-cascade.ts`) : les **deux** engagées d'une rencontre déclarent forfait. L'arbitrage le prononce depuis le dialogue de score (« Les deux (double forfait) »), **uniquement par la validation** (`POST .../resolve` avec `{ doubleForfeit: true }`, exclusif d'un score et d'un forfait nominatif — `DOUBLE_FORFEIT_EXCLUSIVE` ; l'enregistrement le refuse, `DOUBLE_FORFEIT_RESOLVE_ONLY`). En base : `bg_matches.double_forfeit = 1`, `COMPLETED`, **et rien d'autre** — ni vainqueur, ni perdant, ni score : un 0-0 clos sans vainqueur serait un **match nul** partout où l'on relit les colonnes, alors que sans score l'assiette du classement (`playedMatchSql`) l'écarte d'elle-même (la cote Elo transfère d'une perdante à une gagnante, et il n'y en a pas ; les fiches l'ignorent de même). Une seule règle, **les deux perdent**, déclinée par moteur : en **élimination** (et dans l'arbre final d'une BG Survie) les deux sortent, personne ne monte, le match suivant devient une **exemption** — et personne ne tombe au repêchage d'une double élimination, un créneau de perdant ne tenant pas deux perdantes ; en **Suisse** et en **Survie** une défaite pour chacune (un barrage de Survie élimine donc les deux) ; en **qualification BG Survie** chacune perd le score plein du format ; en **multi-phases**, une équipe sortie par double forfait n'est jamais qualifiée, sa place n'étant pas repêchée. `isMatchDoubleForfeit` (statut **et** drapeau) est la seule lecture, `isMatchDrawn` exclut le cas, `hasScoreInput` le compte. **Effets en cascade dans un arbre** : un double forfait pose un **vide**, que le moteur comble seul — exemption, puis match fantôme si deux doubles forfaits se suivent, puis exemption un tour plus loin. Corriger le résultat défait cette chaîne dans les deux sens (`detachDownstreamOutcome`, appelé par `adminResolveMatch` **avant** `finalizeMatch`) : les rencontres closes d'office sont rouvertes et ce qu'elles avaient fait monter redescend ; un créneau garni est **vidé**, `pushTeamToTarget` ignorant un `null`. On défait, on ne recalcule pas — `tryAutoResolveByes` repose ensuite les exemptions encore justes. **Un tournoi clos par la cascade se rouvre** (`reopenTournament`, dernière phase comprise en multi-phases, et de même en BG Survie quand `repairPlayoffBracket` réécrit un tour d'un tournoi clos) : une demi-finale en double forfait fait de la finale une exemption et clôt le tableau dans la même transaction, et corriger ce double forfait laissait sinon un tournoi « terminé » sur une finale que plus personne ne pouvait saisir. Le **verrou suit la chaîne** : `dependentMatches` traverse les rencontres tranchées sans saisie, si bien que c'est la première rencontre réellement disputée au bout qui verrouille (serveur et interface, même parcours ; le serveur charge donc tout le plateau de la phase). L'arbre d'une BG Survie n'a pas de liens : `planNextPlayoffRound` garde les positions (créneau vacant → exemption, deux vacants → rien), la petite finale ne prend que des battues (une seule → 3ᵉ par exemption), et `finalizePlayoffsIfDone` **enchaîne** les tours nés joués — sans quoi l'arbre attendrait un score que personne n'a à saisir. **Classement final** (`podiumRanks`) : une rencontre de podium met deux places en jeu — finale en double forfait → **pas de championne**, finalistes 2ᵉ ex æquo ; petite finale en double forfait → 3ᵉ vacante, les deux à 4 ; finale gagnée par exemption → 2ᵉ vacante, la gagnante de la petite finale reste 3ᵉ. `isEliminationPhaseComplete` (et son pendant SQL dans `sync-scope.ts`) compte un double forfait pour joué. Voir `docs/features/DOUBLE_FORFEIT.md`.
- **Corriger le score d'un tournoi terminé** (`reconcileEndurance` / `reconcileSurvival` / `reconcileSwiss`) : les trois modes à classement sortaient **en tête** de leur réconciliation sur un tournoi `FINISHED`, si bien que corriger le vainqueur de la finale changeait `winner_team_id` en base sans recalculer ni le podium ni `final_rank` — le tournoi gardait l'ancienne championne à son palmarès, que la page (qui rejoue toujours) contredisait. Or `adminResolveMatch` n'a **aucune garde d'état**, par choix (une archive fausse se répare), et `finishTournament` est écrit pour ce cas (`state <> 'FINISHED'` : ni seconde date de clôture, ni seconde annonce Discord). La règle tient en une phrase : **le classement se rejoue, le tournoi ne se rouvre pas** — rejeu et finalisation sont rejoués, la pose d'une manche, d'une ronde, d'un tour d'arbre ou la bascule en play-offs ne l'est pas (sans quoi une correction pouvait reposer une manche à un tournoi clos, que plus rien n'aurait fait avancer, `syncTournamentState` ne visitant que les `RUNNING`). La branche play-offs de l'endurance passe par le chemin ordinaire : `repairPlayoffBracket` ne réécrit jamais un tour portant une saisie, et dans un tournoi clos ils en portent tous. En pratique `match-lock` ne laisse corriger que la **finale** (et la petite finale) : tout ce qui est en amont est verrouillé par ce qui suit. Abandons et pénalités restent, eux, refusés hors `RUNNING`. Le mode `MULTI` garde le défaut (voir `ERREUR.txt`). Voir `docs/features/FINISHED_TOURNAMENT_RECONCILIATION.md`.
- **Dialogue d'édition d'un score** (`app/(secured)/tournois/[id]/_lib/score-form.ts` pur + `_hooks/useScoreForm.ts` + `_components/AdminScoreDialog.tsx`) : deux actions qu'il ne faut pas confondre — **« Enregistrer »** (`PATCH .../scores`) note l'avancement d'une rencontre en cours et n'écrit *que* les deux scores, **« Valider le résultat »** (`POST .../resolve`) désigne la gagnante et propage dans le plateau. D'où trois refus, posés dans le module pur *et* côté serveur : un match jamais joué ouvre sur des **champs vides** et non sur un « 0 – 0 » inventé (ce zéro était enregistrable, et `hasScoreInput` le comptant comme une saisie, il **verrouillait la manche précédente**) ; un match **déjà tranché** n'accepte plus l'enregistrement (`MATCH_ALREADY_COMPLETED` → 409), qui laissait `winner_team_id` et la qualifiée sur l'ancien résultat — un match affiché gagné par l'équipe qui perd ; un **forfait** ne peut désigner qu'une des deux engagées (`INVALID_FORFEIT_TEAM_ID` → 400), faute de quoi `adminResolveMatch` déduisait un vainqueur par défaut. L'affichage est **conditionnel par défaut** : pastille de format seulement s'il y en a un, résultat en base seulement s'il ne se lit pas dans les champs, forfait replié derrière un lien, et trois poids distincts pour les actions (« Valider le résultat » plein, « Enregistrer » en retrait, « Fermer » en lien) — le style désactivé du `.btn` global s'écrit `:global(.btn)`, sans quoi CSS Modules le hache et la règle ne s'applique à rien. Le match est **résolu à chaque rendu** depuis `detail.matches` (comme les dialogues de diffusion et de calendrier), et le hook se réaligne sur l'empreinte du **résultat enregistré** : rien saisi → adoption silencieuse de ce qu'apporte le flux, saisie en cours → bandeau de désaccord plutôt qu'un écrasement muet. Voir `docs/features/SCORE_EDIT_DIALOG.md`.
- **Aperçu du plateau pendant les inscriptions** (`lib/shared/tournament-preview.ts` pur + `lib/server/tournaments/preview.ts`) : le staff (`tournaments`) et le cast (`casting`) voient l'appariement que produirait un lancement immédiat, recalculé à chaque inscription — plutôt qu'une phase de préparation, qui rognerait la fenêtre d'inscription. **Aucune écriture** : ni match ni classement, seulement une lecture des inscrites. L'aperçu voyage dans `TournamentDetail.preview` (`null` sans permission, et dès `RUNNING`), donc il se rafraîchit avec le SSE existant. Il réutilise les fonctions pures du moteur — `bracket-seeds.ts` (extrait de `serialization.ts`, qui le réexporte), `planFirstRound`, `planSurvivalRound`, `planEnduranceRound`, `resolvePhasePlan` — pour ne jamais montrer autre chose que le tirage réel. Voir `docs/features/TOURNAMENT_PREVIEW.md`.
- **Ordre de seeding réordonnable** (`lib/shared/seeding.ts` pur + `lib/server/tournaments/seeding.ts`) : le staff `tournaments` ordonne les inscrites **au glisser-déposer** ou avec des flèches, **jusqu'à la première saisie de score** (même règle que `match-lock`). `bg_tournaments.manual_seeding` bascule Survie / Suisse / Multi du seeding par classement de site vers l'ordre saisi ; l'élimination lisait déjà `registrations.seed`. Un plateau déjà généré mais vierge est détruit puis régénéré. Les commandes vivent **sur les lignes de la liste des inscrites** (`RegistrationsPanel.tsx`, bloc « Inscriptions · ordre de départ ») et non dans un second tableau des mêmes équipes : de deux listes identiques, celle qu'on cherche porte le nom de la chose, et c'était justement celle qui n'avait pas de flèches. **Deux gestes, une seule écriture** : la poignée `⠿` glisse une ligne d'un bloc (mécanique pure dans `lib/shared/drag-reorder.ts` — `dropIndexAt` contre les milieux d'emplacement relevés **une fois** au premier appui, `moveToIndex` en **extraction puis insertion** et jamais en échange, `autoScrollVelocity` pour atteindre un rang hors écran ; `PointerEvent` et `touch-action: none`, l'API HTML5 de glisser-déposer n'existant pas sur mobile), les flèches restent le chemin du clavier — un glissement n'en a aucun — et les deux passent par la même `applyOrder`. La poignée est un `<span aria-hidden>`, jamais un `<button>` : un contrôle focusable qui ignore Entrée et l'espace est un piège. Rien n'est écrit avant le relâchement, Échap annule. La fenêtre d'édition est **dérivée du détail déjà reçu** (pas de requête à part : les flèches arrivent avec la page ; le serveur reste le juge, 409 sur écriture tardive) et le geste déplace la ligne tout de suite, corrigé ensuite par le flux. `TournamentSnapshot.seedingSource` (`MANUAL` / `RANKING` / `REGISTRATION`, règle unique `seedingSource()` partagée avec l'aperçu du plateau) dit si la liste triée par `seed` **est** le tirage : en `RANKING` elle ne l'est pas — le moteur seede depuis le classement du site tant que personne n'a réordonné — et le bloc le dit à côté des flèches. Voir `docs/features/SEEDING_ORDER.md`.
- **Retirer un engagé d'un tournoi** (`lib/shared/entrant-removal.ts` pur + `lib/server/tournaments/registration-removal.ts`) : une inscription ne se défaisait pas. La seule sortie était l'**abandon**, qui exige le tournoi `RUNNING`, n'existe qu'en Survie / Suisse / BG Survie, et laisse l'engagé au classement avec un forfait à son nom — pour un tournoi qui n'a pas commencé, c'est écrire une défaite là où il n'y a jamais eu de match, et surtout une place qui ne se rend pas. Le staff `tournaments` (arbitre compris : c'est le même métier que l'arbitrage, seule la suppression d'un tournoi exige `isAdmin`) efface donc une inscription par `DELETE /api/admin/tournaments/[id]/registrations/[teamId]`, **jusqu'au début du tournoi, pas une seconde de plus**. La borne n'est pas une prudence : au coup d'envoi le tirage est fait — plateau, classements de départ et appariements descendent tous de la liste des inscrites —, et en retirer une après coup laisserait un match sans adversaire. Corollaire, le module n'a **aucun** nettoyage à faire (ni match, ni classement, ni phase : ils naissent tous à la bascule que la fenêtre refuse de franchir), et les deux gestes ne se recouvrent jamais, l'un avant et l'autre après la même borne. L'état est lu **deux fois**, stocké *et* calculé (même paire que `launchBlockReason`) : le premier rattrape un tournoi lancé par anticipation ou clos à la main, le second un tournoi dont l'heure de début est passée sans que la colonne ait été recalée — et le service **synchronise d'abord**, sans quoi le retrait passerait au seul motif que personne n'avait ouvert la page. `lockTournamentRow` est repris tel quel de l'inscription, en **toute première instruction** (même piège `REPEATABLE READ`) ; `resequenceSeeds` referme le trou laissé dans la colonne `seed` et vit dans `seeding.ts`, où vit la règle d'ordre, sans toucher `manual_seeding`. **Aucune équipe ni aucun joueur n'est supprimé** — la fantôme resservira, l'entrée solo est une identité d'engagé. Une ligne au journal Discord, envoyée **depuis la route** (`sendBotLog`) et non par la file : l'auteur est nommé, et une entrée de file n'est qu'un renvoi. Côté interface, le bouton partage la cellule d'actions des flèches de seeding mais **pas leur condition** — l'ordre reste réglable jusqu'à la première saisie de score, donc après le coup d'envoi — d'où trois gabarits de grille exclusifs et un intitulé de colonne qui nomme ce qu'elle contient ; fenêtre fermée, la phrase du module pur prend la place du bouton. Voir `docs/features/ENTRANT_REMOVAL.md`.
- **Édition d'un tournoi après création** (`lib/shared/tournament-edit.ts` pur + `lib/server/tournaments/edit.ts`) : le staff `tournaments` peut modifier un tournoi selon trois fenêtres — `FULL` (tournoi caché, tout éditable), `RESTRICTED` (annoncé mais pas lancé, cinq champs : nom, description, clôture des inscriptions, début du tournoi, effectif maximal), `LOCKED` (en cours ou terminé, rien). Le module pur décide quels champs sont modifiables ; le serveur le rejoue sous `SELECT … FOR UPDATE` pour refuser une modification devenue interdite entre le chargement du formulaire et sa soumission. Validation partagée avec la création (`lib/server/tournaments/validation.ts`) : même barème, mêmes règles d'ordre des dates, pas de divergence possible. La route `PATCH /api/tournaments/[id]/edit` applique une liste blanche sur le corps (seuls les champs de `ALL_TOURNAMENT_FIELDS` passent) et mappe les erreurs HTTP (fenêtre fermée → 409, incohérence → 400). Voir `docs/features/TOURNAMENT_EDITING.md`.
- **Lancement anticipé** (`lib/shared/tournament-launch.ts` pur + `lib/server/tournaments/launch.ts`) : le staff `tournaments` **abrège les étapes d'avant-course** (masqué, annoncé, inscriptions, clôture) et lance le tournoi sur-le-champ — `POST /api/admin/tournaments/[id]/launch`, sans corps. L'édition ne pouvait pas produire ce résultat, et pas par omission : reculer la clôture dans le passé y est refusé (seul, le geste ferait *reculer* le tournoi d'un état), et avancer le début seul ne change rien puisque `computeTournamentState` teste les inscriptions **avant** le coup d'envoi. La règle tient en une phrase : **on ne fait jamais avancer une date, on ne fait que la reculer** — chaque jalon est ramené au plus tôt entre sa valeur et l'instant du lancement, dans l'ordre inverse du calendrier, chacun borné par le suivant déjà résolu (le recul d'une seconde n'est pas décoratif : `computeTournamentState` rend `REGISTRATION` tant que `now <= registrationCloseAt`, bornes comprises). L'ordre chronologique s'en trouve préservé par construction, donc aussi l'invariant « un tournoi caché est toujours `UPCOMING` » : abréger depuis « masqué » **publie** le tournoi au passage, il ne devient jamais « en cours et invisible ». **L'état n'est jamais écrit à la main** — une fois les dates abrégées, `syncTournamentState` lance le tournoi comme il l'aurait fait à l'heure dite, dans la **même transaction**, journal Discord compris : aucun format ne connaît le lancement anticipé, et un format ajouté demain en hérite sans une ligne. Seul refus : « il n'y a plus rien à abréger » (déjà lancé, déjà terminé), sur l'état **calculé**. Partir d'une étape où personne n'a pu s'engager n'est **pas** refusé — le tournoi est alors clos faute d'adversaires, ce que la confirmation annonce avant le clic plutôt que de retirer le droit. Voir `docs/features/EARLY_TOURNAMENT_LAUNCH.md`.
- Bye slots for non-power-of-2 participant counts (`docs/features/BYE_FUNCTIONALITY.md`)
- Variable bracket sizing (`docs/features/VARIABLE_SIZE_TOURNAMENTS.md`)
- **Ronde suisse** (`SWISS`, ouvert à la création — `docs/features/SWISS_MODE.md`) : nombre de rondes fixe, aucune élimination, appariement par groupe de points. Même modèle que la Survie : logique pure dans `lib/shared/swiss.ts` (rejeu, points, départages) + `lib/shared/swiss-pairing.ts` (appariement par **retour sur trace**, qui trouve les combinaisons sans rematch qu'un tirage glouton manque), orchestration dans `lib/server/tournaments/swiss.ts`. `reconcileSwiss` **rejoue** tout depuis l'historique des matchs (`replaySwiss`) — une correction de score se répercute d'elle-même sur le classement et réapparie la ronde suivante tant qu'elle n'est pas entamée ; seuls seed initial et abandons sont stockés en entrée. Piège à connaître : apparier la ronde R se fait sur l'état rejoué **avant** R (`SwissState.before`), sinon les paires déjà posées bloquent leur propre reformation. Départages : Buchholz, Sonneborn-Berger, % de victoires adverses, confrontation directe, puis seed. Seeding par `loadEntrantsBySiteRanking`, comme la Survie et le leaderboard.

### Live Updates (`lib/server/live.ts` + `lib/server/tournament-broadcast.ts`)
Node.js `EventEmitter` singleton publishes tournament events (`updated`, `score_reported`, `score_resolved`), consumed via SSE at `/api/tournaments/[id]/stream`.

**Le flux transporte la donnée, pas un signal.** Le détail d'un tournoi est scindé en `TournamentSnapshot` (identique pour tous) + `TournamentViewerContext` (propre au lecteur — engagement, droits, aperçu du plateau, `canManageLive`) ; `TournamentDetail` reste leur intersection. Tout droit du lecteur doit être câblé sur **les deux** portes, la route du flux et la lecture REST de secours : le flux étant le chemin nominal, un droit posé sur la seule seconde n'arriverait qu'après une coupure du direct. Une **salle** par tournoi suivi (`tournament-broadcast.ts`) calcule et encode l'instantané **une fois** et l'écrit à tous les abonnés : le coût en base ne dépend plus du nombre de spectateurs. Un **budget de sortie** par salle (512 ko/s) élargit la fenêtre quand le plateau est lourd — un tournoi à 128 équipes pèse 154 ko et ses inscrits sont tous prioritaires. Dans le cas nominal, la page ne fait **aucune** requête REST — `GET /api/tournaments/[id]` n'est plus qu'un chemin de secours.

Deux **paliers de fraîcheur** (`lib/shared/refresh-tiers.ts`, pur, source unique des cadences) : `PRIORITY` (staff `tournaments`, cast `casting`, engagés du tournoi) reçoit dans la seconde, `STANDARD` (spectateurs) par fenêtres plus larges. Le palier est décidé par le serveur à la connexion, jamais déclaré par le client ; `refresh-tiers.ts` ne connaît aucun rôle, c'est la route du flux qui traduit les permissions en palier.

Trois choses remplacent le F5 : le flux qui pousse, le **retour sur l'onglet** (`useAutoRefresh`, étranglé), et le calcul **client** des bascules d'état à partir des dates publiques (`lib/shared/tournament-state.ts` + `useScheduledBuckets`) — une carte passe à « Inscriptions » à la seconde dite, sans requête. La reconnexion SSE n'abandonne jamais (attente exponentielle plafonnée + gigue).

Côté charge : cache mémoire **à vol unique** (`lib/server/cache.ts`) sur l'instantané, la liste publique et les agrégats de la vitrine — cent appels concurrents partagent un seul calcul ; invalidation centralisée dans `tournaments/notifications.ts` ; plafonds de débit larges (`lib/server/rate-limit.ts` + `api-guard.ts`, tous déclarés dans ce dernier — une identité absente n'est **pas** plafonnée, sans quoi tous les visiteurs partageraient un seul seau quand le proxy ne pose pas `X-Forwarded-For`) ; étranglement de `syncVisibleTournaments` porté de 1 s à 15 s. Cette passe n'entretient que les tournois **qui ont quelque chose à faire** (`lib/server/tournaments/sync-scope.ts`) et ouvre **une transaction par tournoi** : elle repassait sur tous les tournois non terminés dans une transaction unique, si bien que sa durée était la somme des entretiens (des minutes sur une base seedée) — et, la lecture de la liste l'attendant, l'accueil et toute écriture sur `bg_tournaments` attendaient derrière. Le repérage se fait en deux temps : les **jalons de calendrier** en mémoire avec `computeTournamentState` (la règle est partagée, la réécrire en SQL en ferait une seconde) et les **entretiens dus** par `EXISTS` indexés, une condition par tâche de la branche `RUNNING` de `syncTournamentState`. Voir `docs/features/REALTIME_REFRESH.md` et `docs/features/TOURNAMENT_SYNC_SCOPE.md`.

### Bot Integration (`lib/server/bot-integration.ts`)
HTTP calls to an internal Discord bot (configurable host/port). Gracefully degrades if bot is unreachable. Used for: auth DM codes, score conflict logging, stats, **fréquentation du site**. Le sens des appels est toujours app → bot : pour exposer une donnée du site dans une commande Discord, l'app **pousse** un instantané sur `/internal/*` — le bot n'appelle jamais le site en retour.

**Le flux d'activité du bot est public, donc anonymisé** (`lib/shared/bot-feed-redaction.ts`) : le bandeau « Flux temps réel » de `/bot` se lit **sans compte**, et le bot y nomme le joueur par son **identifiant Discord** — dans le texte de l'évènement (« Code DM envoyé à 100000000000000001 ») comme dans un champ à part (`target`). Un identifiant n'est pas un secret, mais c'est une **coordonnée** : il suffit à écrire à la personne, horodatage de sa connexion à l'appui — or le site ne publie nulle part ailleurs le moyen de joindre un joueur, même certifié (`canViewDiscordTag` n'ouvre **jamais** au public). Le relais SSE (`app/api/bot/feed/stream`) efface donc tout *snowflake* à la **sortie**, seul endroit qui voie l'intégralité de ce qui part vers un navigateur : il couvre du même geste le **rattrapage d'historique** (`getBacklog` rejoue à chaque connexion des lignes déjà écrites avec leur identifiant, que corriger le bot ne réécrirait pas) et l'évènement qu'un module ajouterait demain — la règle ne connaît **aucun type d'évènement**. Un champ dont la valeur *est* un identifiant disparaît, une phrase qui en contient un le garde masqué. Deux précautions dans le relais : l'effacement travaille sur des **lignes entières** (une trame TCP coupe un identifiant en deux morceaux qu'aucun motif ne reconnaît plus), et la ligne `id:` est laissée **intacte** — c'est la clé de reprise `Last-Event-ID`, la rogner ferait rejouer tout l'historique à chaque reconnexion.

### Page `/bot`
La vitrine du bot ne montre que ce qu'elle peut tenir. Deux blocs en ont été retirés parce qu'ils **avaient l'air** branchés sans l'être : **« Modules »**, qui ne tenait que si le bot exposait `/internal/servers/:id/modules` et rendait sinon son en-tête (« 0 INSTALLÉS · 0 ACTIFS ») au-dessus d'une grille vide ; et la liste **« Slash commands »**, huit commandes écrites en dur dans `components/bot/mocks.ts` — une documentation fausse qui a l'air d'une documentation, qu'aucun test ne pouvait contredire puisque le bot vit dans un autre dépôt. La section renvoie désormais à `/bot/docs`, qui sert le Markdown du bot **à chaud** : une correction là-bas y apparaît dans la minute. Nuance à ne pas gommer — seul le **corps** des pages est relu chez le bot, les titres et résumés affichés venant de `BOT_DOC_SECTIONS`, registre de ce dépôt (c'est lui qui borne les fichiers lisibles, garde-fou anti-traversée de chemin) ; l'intitulé de la section dit donc « contenu relu » et non « mise à jour continue ». Les types, l'appel sortant, les pictogrammes et les règles CSS sont partis avec eux — une feuille qui garde des règles orphelines finit par les faire ressusciter. Enfin la colonne « STATUS » du tableau des serveurs s'intitule **« ÉTAT DU RELAIS »** (jamais « RELAIS » seul : la colonne voisine compte les relais de 30 jours, deux en-têtes homonymes se reliraient l'un pour l'autre) et se lit en français — « À jour » / « Retard » / « Hors ligne » : les valeurs renvoyées par le bot (`ok`/`lag`/`off`) sont inchangées, c'est leur traduction qui manquait, « lag » est le vocabulaire du bot, pas celui du lecteur. La règle vit dans `lib/shared/bot-relay-status.ts`, module **pur** — elle se teste sans rendu — et **nomme l'état qu'elle ne connaît pas** (« Inconnu ») plutôt que de rendre une cellule vide : `fetchBotServers` fait un simple `as` sur du JSON reçu par le réseau, une recherche directe dans un `Record` rendrait `undefined` au premier état ajouté côté bot, et React n'afficherait rien — la panne muette que cette page vient justement de chasser. Le **ton** (la classe CSS) sort du registre et jamais de la chaîne reçue. Chaque canal porte ce qu'il peut, sans qu'aucun promette plus : le **libellé** dit l'état à tout le monde, le `title` en donne la définition au pointeur, un `aria-label` qui **commence par le texte visible** (WCAG 2.5.3) la donne aux technologies d'assistance — un visiteur voyant au doigt n'a que le libellé, et c'est précisément pour lui qu'il fallait le rendre lisible. Pas de légende sous le tableau : le renommage est ce qui devait la rendre inutile, et c'est une décision, pas un oubli. Le sous-titre de la case « Status » suit la même règle dans `lib/shared/bot-status-summary.ts` : il **dit l'état affiché au-dessus** au lieu d'une phrase fixe (des « modules nominaux » annoncés sous un `DOWN`, et parlant d'une grille retirée), et distingue **deux silences** — « le bot n'a pas répondu » (`UNREACHABLE`) et « le bot a répondu un état que la page ne sait pas lire » (`UNREADABLE`) : la case montrant la valeur reçue en gros, les confondre remettrait une phrase qui contredit la valeur juste au-dessus. Deux pièges de mise en page que le renommage a réveillés, les libellés français étant plus longs et **de longueurs inégales** : la colonne a sa **largeur fixe** (115 px, `nowrap`) — à 70 px l'en-tête passait sur deux lignes et les serveurs arrêtés avec lui ; et sous 640 px les pistes restantes sont **fixes elles aussi**, jamais `auto` — l'en-tête et chaque rangée étant des grilles **séparées**, une piste `auto` se dimensionne sur le contenu de *sa* ligne, si bien que « ● À jour » et « ○ Hors ligne » posaient la colonne à deux abscisses différentes.

## Preview / dev auth bypass

Pour vérifier les pages protégées (`/tournois`, `/equipes`, `/joueurs`, `/profil`, etc.) sans passer par Google OAuth ni le code Discord, définir `DEV_AUTH_USER_ID=<id>` dans `.env` (par exemple `321` pour le user admin). La fonction `getCurrentUser()` dans `lib/server/auth.ts` retournera ce user **uniquement si `NODE_ENV === "development"`** (c.-à-d. `next dev`), en court-circuitant le cookie de session — toutes les routes API et le `app/(secured)/layout.tsx` s'authentifient automatiquement. **Redémarre le dev server après modification de `.env`** pour que Next.js prenne en compte la nouvelle valeur. Désactiver = supprimer/vider la var. La garde-fou est double et en **liste blanche** (`NODE_ENV === "development"` ET ID entier valide) : le bypass est donc inactif en prod, en `test`, en `staging`, ou si `NODE_ENV` n'est pas défini. Ne JAMAIS définir cette var en prod.

## Jeu de test (`npm run seed`)

**Le seed refuse de tourner en production** (`NODE_ENV=production` → sortie 1). Il ne viderait pas grand-chose là-bas — aucune donnée de prod ne porte les préfixes de test — mais il **créerait** la matrice entière dans la base que le site sert. Le refus porte sur `NODE_ENV` et non sur `DB_HOST` : la base écoute sur `127.0.0.1` des deux côtés, l'hôte ne distingue rien. Ce refus **remplace une protection accidentelle** : le script n'importe que `dotenv/config`, qui ne lit que `.env`, si bien qu'il mourait sur le serveur faute de configuration — jusqu'au jour où quelqu'un y poserait un `.env`. Les scripts faits **pour** la production importent, eux, `lib/server/script-env.ts` (ordre des fichiers dans `lib/shared/env-files.ts`, calqué sur Next : `.env.<env>.local`, `.env.local`, `.env.<env>`, `.env`).

`npm run seed` **écrase** les données de test (tout ce qui est préfixé `Test_` / `Test - `, plus la table `bg_bureau_members`) puis régénère une matrice de cas destinée à couvrir un maximum de combinaisons en une exécution :

- **Comptes** (`lib/server/seed.ts` → `SPECIAL_USERS`) : admin, un compte par rôle de plateforme (`ARBITRE`, `CASTER`, `COMMUNITY_MANAGER`, `RECRUTEUR`) + un cumul, profil tout privé / tout public, mineur, majorité inconnue, sans tags de jeu, sans équipe, compte anonymisé. L'id de l'admin est affiché en fin de seed : c'est la valeur à mettre dans `DEV_AUTH_USER_ID`.
- **Équipes** : rosters complets avec rôles cumulés (`OWNER`/`CAPITAINE`/`TANK`/`DPS`/`HEAL`/`COACH`/`MANAGER`), plus les cas limites (équipe à un seul membre, équipe sans joueur, avec/sans logo) et ~140 équipes de remplissage pour les gros brackets.
- **Tournois** (`lib/server/seed-cases.ts` → `TOURNAMENTS`) : la matrice **état × format × effectif × situation de match**. 4 états, 5 formats (`SINGLE` avec/sans petite finale, `DOUBLE`, `SWISS`, `SURVIVAL`, `MULTI` — dont un cas sous-rempli où la première phase est sautée), effectifs de 0 à 128 (puissances de 2 et effectifs à byes), survie impaire 3/5/7/9/11/15/21 (barrage) avec cadences 1/2/3 et forfaits, plus les états intermédiaires du cycle de report (report en attente, conflit de scores, délai dépassé).

Ajouter un cas = ajouter une entrée à `TOURNAMENTS` ; `lib/server/seed-cases.ts` est volontairement sans accès base pour rester testable (`tests/lib/server/seed-cases.test.ts` garde la couverture de la matrice). Les résultats de matchs sont tirés par un LCG réamorcé par tournoi : **le seed est reproductible** d'une exécution à l'autre.

## Key Conventions

- All UI text is in **French**.
- **Error and success messages** must always appear as overlay notifications (bottom-left) via `useToast()` from `@/components/ui/toast`. Never render them inline in the page body. Use `showError(message)` for errors and `showSuccess(message)` for success feedback.
- `lib/server/*` is server-only code; never import from client components.
- `lib/shared/*` is safe to import anywhere.
- `normalizePseudo()` / `slugifyPseudo()` for username normalization, `toIso()` for dates, `parseRoles()` for JSON role arrays — always use these helpers, don't re-implement.
- User roles on teams are cumulative strings stored as JSON arrays (`OWNER`, `CAPITAINE`, `MANAGER`, `COACH`, `TANK`, `DPS`, `HEAL`).
- **Rôles de gestion d'une équipe** (`lib/shared/team-roles.ts`, pur) : sur les sept rôles d'équipe, deux seulement donnent la main — `OWNER` et `MANAGER`. Les cinq autres sont **sportifs** : ils décrivent une place dans le roster, pas un pouvoir. La ligne de partage n'est donc pas « propriétaire ou pas » mais **identité, propriété et existence de l'équipe** d'un côté (nom, sigle, transfert, dissolution — `OWNER` seul) et **conduite de l'équipe** de l'autre (logo, membres, rôles, invitations, **l'inscription à un tournoi et le retrait du tournoi** — la paire). Engager une équipe vaut promesse de se présenter : cela l'expose entière à un forfait et occupe une place que d'autres attendent, d'où le même rang qu'inviter ou exclure — un `DPS` est refusé en `403 NOT_TEAM_MANAGER`. **L'abandon relève de la même qualité, et pour une raison plus forte encore** : il retire l'équipe du tournoi séance tenante — capital à zéro en BG Survie, éliminée ailleurs — et rien ne le défait, alors qu'une inscription se défait justement par un abandon. Le geste le plus lourd des deux était pourtant le moins gardé : n'importe quel membre du roster pouvait désengager une équipe qu'il n'avait pas le droit d'engager. `hasTeamManagementRole` est l'**unique** implémentation, partagée par `userCanManageTeam` (gestion du roster), `registerCurrentUserTeam` (écriture, rôles relus **dans la transaction** avec l'équipe active : le droit se juge à l'instant de l'écriture), `resolveUserEntrant` (qui rend l'engagé **et** la qualité d'agir en son nom, sur la même ligne d'appartenance — un second appel les lirait dans deux états différents ; c'est par lui que passe l'abandon) et `canUserRegister` (qui ferme le bouton plutôt que de l'annoncer pour rien). Le **tournoi individuel** échappe à la règle : le joueur n'engage que lui-même, par une entrée solo qui n'a ni membre ni rôle. Côté interface, la qualité voyage dans `TournamentViewerContext.canRegisterEntrant` — elle tient à la personne, pas au plateau, donc le client la rejoue d'un instantané à l'autre au lieu de la recalculer — et `registerBlockedNotice` met une phrase là où le bouton aurait été, ce refus étant le seul qui ne se lise pas tout seul sur la page. Voir `docs/AUTHORIZATION_RULES.md` §3 et §4.2.
- Admin users have `is_admin = true` in `bg_users`; admin-only routes live under `app/api/admin/`.
- **Équipes fantômes** (`bg_teams.is_ghost`) : équipes sans joueur, créées et administrées par le staff `tournaments` pour les tournois (remplissage de bracket, équipe invitée). La dérogation d'administration passe par le paramètre `viewerManagesGhostTeams` des fonctions de `teams-service`, et ne s'applique **jamais** à une équipe réelle. Logique dédiée dans `lib/server/ghost-teams-service.ts`. **Inscription en lot** (`lib/shared/ghost-registration.ts` pur + `registerGhostTeams`) : remplir un plateau de trente se faisait une équipe à la fois, et rien n'empêchait de reproposer une déjà engagée — le refus n'arrivait qu'après l'aller-retour. `POST .../ghost-registrations` prend désormais `{ teamIds }`, une liste : inscrire une fantôme et en inscrire trente suivent le même chemin, il n'y a pas deux règles à tenir. **Tout ou rien** — une transaction, un seul `publishUpdatedEvent`, défaite au premier refus ; un résultat partiel obligerait à recouper la sélection contre la liste des inscrites et distribuerait les rangs de départ à un préfixe arbitraire. En contrepartie le refus **nomme** l'engagé qui a bloqué (`teamId` joint au corps) quand il en désigne un, jamais sur `TOURNAMENT_FULL` ni `REGISTRATION_CLOSED`, qui valent pour le lot entier. Le plafond est relu **à chaque insertion** dans la transaction, et `registerTeam` prend un `SELECT … FOR UPDATE` sur la ligne du tournoi avant de compter : l'unicité `(tournament_id, team_id)` protège du doublon, pas du dépassement d'effectif. Le verrou est pris en **toute première instruction** de la transaction, par les deux points d'entrée (`lockTournamentRow`) et non seulement dans le tronc commun : sous `REPEATABLE READ`, c'est la première lecture *ordinaire* qui fige l'instantané, et une lecture verrouillante n'en crée pas — un simple `loadTournamentRow` placé avant le verrou fige le monde *avant* l'attente, et le comptage qui suit compte un effectif périmé. Le contrôle « c'est bien une fantôme » est lui aussi verrouillant (`ORDER BY id FOR UPDATE`), sans quoi une attribution validée pendant qu'on coche resterait invisible. Un lot vaut **32 engagés au plus**, nombre repris de `MAX_PENDING_PER_TRANSACTION` (`bot-logs.ts`) : au-delà, `queueBotLog` abandonne et les inscriptions s'écriraient sans leur ligne de journal ; le même nombre borne la durée du verrou. Les déjà engagées sont écartées **en base** (`listGhostTeams(tournamentId)`), pas masquées côté client. En tournoi individuel le lot fonctionne tel quel — un « joueur invité » *est* une fantôme, seul le vocabulaire change ; une **entrée solo**, elle, naît avec `is_ghost = 0` et se fait refuser par le même `NOT_A_GHOST_TEAM` qu'une équipe réelle. Voir `docs/features/GHOST_TEAMS.md`.

- **Retour en arrière — reculer d'une manche, à répétition** (`lib/shared/tournament-rollback.ts` pur + `lib/server/tournaments/rollback.ts`) : une manche saisie sur de mauvais appariements verrouille la précédente (`match-lock`, **y compris pour un admin**), et le seul chemin de sortie était d'effacer les scores un par un dans le bon ordre, sur un plateau qui peut compter des dizaines de rencontres. `POST /api/admin/tournaments/[id]/rollback` (staff `tournaments` — c'est un acte d'arbitrage, la version en gros de la correction de score ; seule la suppression exige `isAdmin`) efface le dernier stade joué **d'un coup**, et le geste **se répète** : un cran par clic, du dernier stade jusqu'au premier. C'est un outil de rattrapage — on répare une erreur d'une manche ou deux —, d'où des **pas** plutôt qu'un « revenir à la manche N » qui obligerait à choisir sans rien voir. **Tous les formats, à tout moment**, tournoi terminé compris. La clé est le **stade** et non le numéro de manche, qui ne situe un match que là où il n'y a qu'une série : un couple `(rang de phase, index)`, l'index venant du **graphe** quand le groupe de matchs porte des liens `next_*` (`maxProfondeur − profondeur`, la profondeur étant le **plus long** chemin vers une racine) et du **numéro de manche** sinon. Les deux familles se distinguent par les liens eux-mêmes, jamais par le nom du format — d'où un module qui traite le multi-phases sans rien connaître des phases. Le graphe redonne exactement les manches en élimination simple, range la **petite finale** au stade de la finale sans cas particulier (c'est une racine, comme elle), et ordonne la **double élimination** dans son ordre réel (`UB1 · {UB2, LB1} · LB2 · …`, chaque stade ne contenant que des rencontres indépendantes entre elles) ; le plus court chemin rangerait la finale du tableau principal avant des rencontres qui la précèdent. « Dernier stade joué » = le stade maximal **portant une saisie** (`hasScoreInput`), et non le dernier *existant* : en élimination tout le plateau naît au lancement. Corollaire utile : ce qui suit est forcément vierge, on n'efface jamais un résultat qu'on n'a pas montré. Le stade est **vidé, pas supprimé** — un identifiant de match est une adresse publique (lien profond, horaire, diffusion) ; seul ce que le moteur sait **reposer** est supprimé : les manches à venir d'un format à classement et le plateau d'une **phase ultérieure**. Le détachement d'un plateau est **volontairement large** (tout ce qui suit), donc il vide aussi des créneaux que le stade défait n'alimentait pas — en double élimination un match peut être alimenté par un match situé **deux stades plus haut** : défaire le deuxième tour de repêchage détachait la finale du tableau principal, dont les deux engagées venaient d'un match joué et non effacé, et rien ne les reposait (`pushTeamToTarget` n'est appelé qu'à la résolution d'un match). D'où un passage de **re-remplissage**, qui est au plateau ce que le rejeu est aux modes à classement : toute rencontre encore tranchée dont la cible vient d'être détachée y repose vainqueur et perdant, par la **même** `pushTeamToTarget` que l'arbitrage. Corollaire : une rencontre détachée est vidée de son **résultat** comme le stade défait — elle n'a pas été jouée, mais le moteur a pu la *résoudre* (un bye), et lui laisser son vainqueur donnerait une ligne qui annonce un gagnant sans participante, que `isEliminationPhaseComplete` compterait pour jouée. **Le moteur n'a presque rien à apprendre** (les modes rejouant depuis l'historique, il suffit d'effacer puis d'appeler la chaîne de réconciliation d'une correction de score, `reconcilePhases` compris) — *presque*, car **quatre états ne se déduisent pas des matchs** : le **curseur de manche** (`swiss_current_round` / `survival_current_round` / `endurance_current_round`, sur `bg_tournaments` ou sur `bg_tournament_phases` selon le rang de phase — sans ce recul, défaire la manche 1 d'une ronde suisse à huit créait une « ronde 3 » pendant que la 1 restait vierge, vu en base et pas en test) ; **`endurance_playoffs_started`**, relu sur ce qui reste au-delà de `PLAYOFF_ROUND_OFFSET` ; **l'état des phases** (c'est le seul endroit du projet qui fasse *reculer* un multi-phases, `reconcilePhases` ne sachant qu'avancer : phase visée remise en `RUNNING` et redevenue courante, rangs et qualifications effacés, phases suivantes remises en `PENDING` avec **suppression** de `bg_tournament_phase_teams` et des classements de leurs moteurs — ces initialisations sont des upserts, une ancienne liste de qualifiées survivrait à la nouvelle) ; et **l'état du tournoi**, un tournoi terminé étant **rouvert** (`state`, `finished_at`, `final_rank`) *avant* toute écriture, la réconciliation lisant cet état pour décider ce qu'elle a le droit de reposer. `finishTournament` ne closant qu'une fois (`state <> 'FINISHED'`), le tournoi se reclôt tout seul, nouvelle championne comprise. L'arbre d'endurance se défait **en deux temps** et non un : le premier vide le tour, le second (une fois le premier tour vierge) vise la dernière manche qualificative et emporte l'arbre entier — un pas unique laisserait le tournoi dans un état que le moteur traverse sans s'y arrêter, la qualification étant toujours achevée. Abandons, pénalités, inscriptions et seeding restent : ce sont d'autres entrées du rejeu. Trois refus seulement : **plus rien à défaire**, tournoi **pas encore commencé**, et le stade **a bougé** (`expectedStage`, clé `"<phase>:<index>"` : le dialogue *montre* les rencontres qu'il efface et le plan est recalculé côté serveur — sans ce garde-fou, un score saisi entre l'ouverture et le clic faisait effacer des résultats que personne n'avait vus ; il ne peut que faire refuser, jamais déplacer). Interface : bouton dans la **zone de danger** (qui s'ouvre donc à deux publics, chaque bloc gardant sa garde), rendu **même désarmé** avec son motif ; le dialogue **montre les scores qui vont partir**, seule sauvegarde possible, une case à cocher arme le geste, et un second encart annonce la réouverture d'un tournoi terminé. Deux libellés parce qu'une manche est féminine et un tour masculin (`rollbackStageLabelWithArticle`), et sur un plateau le numéro annoncé est le **rang du stade** et non la manche stockée. Une ligne au journal Discord, jamais au canal arbitre, rédigée depuis le libellé du **serveur**. Voir `docs/features/ROUND_ROLLBACK.md`.

Les deux dernières n'élargissent rien : ce sont les cas où « effacer » ne veut rien dire. Décision **conservatrice** — dans le doute on anonymise, les deux erreurs ne se valant pas. Les cascades font l'effacement ; deux choses demandent un geste, faute de clé étrangère. `bg_site_visits` (une cascade y effacerait l'historique de fréquentation) : le lien est **détaché** (`user_id = NULL`) et non la ligne supprimée — ce qu'il faut retirer est le lien vers une personne, pas le fait qu'une page ait été vue —, et **avant** l'effacement, sans quoi la ligne ne serait plus retrouvable. Traces et écriture vivent dans **une seule transaction**, ouverte par un `SELECT … FOR UPDATE` sur la ligne du compte en toute première instruction (même piège `REPEATABLE READ` qu'ailleurs) : elle ferme l'état intermédiaire des deux écritures *et* la seule course qu'aucune clé étrangère ne tranche — l'**entrée solo**, `ensureSoloEntry` posant le **même** verrou avant d'en créer une. Les trois questions tiennent en **une** requête : un `await` entre elles laisserait créer un tournoi entre la deuxième et la troisième. La confirmation **décrit ce qui va se passer** (`GET /api/profile/deletion`, lecture seule, appelée sur le chemin de la suppression et jamais au chargement du profil) et `DELETE /api/profile` **rend le plan appliqué**, l'écriture reposant la question sur son propre instantané. Le **mode ne suffit pas** à rédiger la phrase : « tes statistiques resteront, elles appartiennent aussi aux équipes que tu as affrontées » est faux de qui n'est retenu que par une équipe possédée ou un tournoi organisé — d'où un **motif** (`AccountRetentionReason`), une phrase par motif, et celle du propriétaire d'équipe qui nomme le geste levant la conservation (transférer ou dissoudre). `accountDeletionPlan` construit mode et motif **ensemble**, deux calculs séparés pouvant se contredire dans une même réponse. Le bouton se ferme **avant** l'aperçu : `window.confirm` ne bloque le second clic que tant qu'il est la première instruction, un `await` devant lui rouvrant la fenêtre du double envoi. Une clé étrangère peut refuser **malgré** le verrou (ses contrôles lisent la dernière version commitée, pas l'instantané) : `isReferencedRowError` traduit le message brut de MySQL — qui nomme base, table et contrainte, et partirait tel quel dans la notification — en `ACCOUNT_STILL_REFERENCED`, rendu en français par `accountDeletionErrorMessage`, qui nomme la suite (réessayer, le second passage anonymise). Côté annuaire, `/joueurs` masque les comptes anonymisés **par défaut** derrière une case qui les compte, sans jamais les retirer de la réponse — c'est le seul moyen de retrouver un adversaire d'un tournoi passé ; leur carte est en retrait, mais **jamais** par une opacité posée sur la carte (elle emporterait la mention qui l'explique) ni sur `.plTeam` (un contexte d'empilement y ferait passer le lien d'équipe sous la plaque `.cardOverlay`, menant à la fiche du joueur). Le verrou ne couvre pas ce qui **reprend après lui** : une sauvegarde de profil ou un téléversement d'avatar déjà partis attendent le commit puis reposaient l'identité réelle sur la ligne anonymisée (et, par `syncSoloEntryIdentity`, jusque sur la carte de match en direct de la vitrine) — d'où un `AND is_deleted = 0` sur les deux écritures, relu sur `affectedRows` (mysql2 pose `FOUND_ROWS`, le nombre compte les lignes **appariées**) : l'avatar rend un booléen que la route traduit en ménage du fichier déjà écrit, le profil lève `ACCOUNT_DELETED` → **409**, rendu en français par `accountDeletedWriteMessage`. Et une ligne anonymisée garde un pseudo : `getUserIdByPseudo`, unique traduction « pseudo → compte à rattacher » (invitation dans une équipe, reprise d'une fantôme), filtre `is_deleted = 0` — sans quoi une demande d'adhésion déposée avant la suppression faisait **rejoindre** le roster à un compte qui ne peut plus ouvrir de session. La même seconde d'écart vaut pour ce qui repose une **porte d'entrée** : `writeVerifiedTag` et les cinq écritures de `linkOAuthIdentity` (`discord_id`, `google_sub`, `blizzard_sub` — les colonnes mêmes par lesquelles on se connecte) portent la condition, comme le **détachement** l'avait déjà ; sans elle, un compte « supprimé de façon irréversible » redevenait joignable par OAuth, tag certifié republié à l'arbitrage. Dernier chemin refermé, celui qui ne passe par aucun pseudo : une **demande d'adhésion** restée `PENDING` s'accepte sur un identifiant, et faisait rejoindre un roster vivant à un compte supprimé — `anonymizeAccount` passe donc en `CANCELLED`, dans sa transaction, tout ce qui pend au nom du compte (le mode « effacement » n'a rien à faire, la cascade l'emporte). `adoptRemoteAvatar` est la plus longue de ces courses (un téléchargement sortant sépare sa lecture de son écriture) et la seule qui laisse un **fichier** derrière elle : l'écriture refusée reprend donc la photo qu'elle vient de poser. Enfin la confirmation ne part plus d'une hypothèse : l'aperçu injoignable donnait la phrase de `TOURNAMENTS` (« le compte devient anonyme, tes statistiques restent ») quand le serveur, qui re-décide sur son instantané, pouvait **effacer entièrement** — d'où `RETENTION_UNKNOWN`, une troisième phrase qui ne promet ni conservation ni effacement, et qui porte le `default` du `switch` (une valeur inattendue doit mener à la description la plus prudente, pas à la plus définitive). **L'effacement réveille des cascades que l'anonymisation n'exécutait jamais** : `bg_team_invitations.created_by` était `NOT NULL ON DELETE CASCADE`, si bien qu'un gérant sans historique emportait en partant les invitations encore en attente chez des tiers — la colonne devient nullable en `SET NULL` (l'invitation est l'acte de l'**équipe**, la colonne n'est lue nulle part, et `bg_endurance_penalties.created_by` tranche déjà ainsi) ; à l'inverse `bg_discord_login_challenges` n'a **aucune** clé étrangère (elle est indexée sur un identifiant Discord) et n'est purgée que par la demande d'un autre joueur — ses lignes sont donc effacées dans la transaction, l'identifiant relevé **sous le verrou** avec le chemin de l'avatar. Enfin la suppression d'avatar écrit **la base avant le fichier** et refuse en 409 comme le téléversement : l'ordre inverse laissait `avatar_url` pointer sur un fichier disparu quand l'écriture échouait. Voir `docs/features/ACCOUNT_DELETION.md`.

Le lien du pied de page, lui, n'est **pas** du code — c'est une donnée éditable (`bg_settings.contact_discord_url`) que corriger le dépôt ne corrige pas : `database.ts` remplace au démarrage les `SUPERSEDED_DISCORD_INVITE_URLS` **et seulement celles-là**, une adresse que le staff a choisie lui appartenant. Le **compteur de membres** de l'accueil se lit sur l'API publique des invitations (`?with_counts=true`) et non par le canal interne du bot : sans jeton ni identifiant de guilde, il compte exactement **le serveur que le bouton d'à côté fait rejoindre** — un identifiant de guilde rangé en parallèle dériverait au premier changement d'invitation, et le site annoncerait la fréquentation d'un serveur vers lequel il ne mène plus. Refus en `null`, **jamais en zéro** (« Discord n'a rien dit » et « le serveur est vide » ne sont pas le même fait, et le second est faux) ; cache de 5 min **hors du préfixe `landing:`**, sans quoi un score reporté relancerait un appel sortant, et **le refus y est retenu lui aussi** — retenter un plafonnement à chaque rendu le prolonge. Le bloc de l'accueil est **une seule ancre** portant chiffre et bouton, sans `aria-label` (son nom accessible *est* son texte visible, WCAG 2.5.3), et il garde son invitation quand le chiffre manque. Voir `docs/features/DISCORD_COMMUNITY.md`.

- **Cases à cocher et boutons radio** (`app/globals.css`) : l'apparence est posée **sur l'élément** (`input[type="checkbox"]`, `input[type="radio"]`), jamais sur une classe ni un composant — huit écrans en posent une nue (équipes invitées, options de format, retour en arrière, filtres de recrutement…) et aucun ne l'habillait : la case restait celle du système, carré blanc à la taille de l'OS sur un fond noir profond, et deux écrans voisins n'avaient pas la même. Le seul réglage qu'on trouvait ici ou là, `accent-color`, ne teinte que la case **cochée** : décochée, elle restait blanche. Posée sur l'élément, la règle couvre la case ajoutée demain sans que personne ait à s'en souvenir — c'est la seule façon de fermer une panne qui tient justement à ce qu'on l'oublie. Trois détails à connaître : la coche est une **image de fond** et non un `::after` (un input est un élément remplacé, ses pseudo-éléments ne sont pas garantis) ; `appearance: none` **retire l'anneau de focus**, qu'il faut donc redonner (`:focus-visible`) sous peine de rendre le parcours clavier invisible ; et **toute règle visant un `input` nu** (`.field input`, `.search input`) a la **même spécificité** que celle-ci : elle la déborde sur les propriétés qu'elle déclare, et une case posée dans un `.field` héritait ainsi du rembourrage d'un champ de saisie — donc, `appearance` retirée, une case rectangulaire — et de son anneau vert au clic. Ces règles portent désormais `:not([type="checkbox"]):not([type="radio"])`, et un test balaie **toutes** les feuilles de `app/` et `components/` — `globals.css`, les `*.module.css` et les feuilles simples de `/bot` — pour qu'aucune ne recommence : le sélecteur qui nomme son type (`input[type="date"]`) reste libre, seul l'`input` nu est tenu. Un style **en ligne** bat toute feuille, d'où un second balayage des `.tsx` — deux écrans posaient un `width`/`accentColor` en ligne et gardaient donc la case que la règle venait d'uniformiser. `Coche` (pastille à part entière, `components/Coche.tsx`) n'y échappe pas par spécificité mais par **masquage** : son input reste habillé, il ne se peint simplement pas — d'où un anneau de focus **relayé en CSS** au frère de l'input (`.coche-input:focus-visible ~ .coche-pill`, teinte du thème passée en variable) et non tenu dans un état React : `:focus-visible` bascule aussi quand une touche est pressée sur un élément **déjà** focalisé, et aucun évènement ne le dit. Les deux contrôles s'écrivent **ensemble**, un radio n'étant qu'une case ronde — `MatchLiveDialog` les montre justement l'un sous l'autre, et n'en habiller qu'un rouvrait la panne sur le panneau d'à côté. La bordure **est** le contrôle tant qu'il est décoché — rien d'autre ne le dessine —, d'où une valeur propre plutôt que `--line-strong`, qui rendait ≈ 2,1:1 sur le fond du site là où un contour de contrôle en demande 3 (WCAG 1.4.11). Dernier point, en **contrastes forcés** on rend la main au système (`@media (forced-colors: active)` → `appearance: auto`, et la **boîte** avec le dessin — `width`/`height: auto`, `display: inline-block` : `appearance` rend la marque, pas les métriques, et le mode va de pair avec le grossissement du texte sous Windows, où une case native épinglée à 16 px se rogne) : le mode force la couleur de fond mais **pas** l'image, si bien qu'une coche presque noire finirait sur un fond noir imposé et que cochée vaudrait décochée ; l'anneau de focus étant un `box-shadow`, lui aussi supprimé, une `outline` le remplace — posée sur la **pastille** pour `Coche`, l'`outline` de la case ne peignant rien là où la case est masquée. L'état **désactivé** se dit en couleurs et non en `opacity` : une opacité se multiplie avec celle d'un parent et la bordure, seule à dessiner le contrôle décoché, finit effacée par le produit des deux — la carte verrouillée de `FormatSettings` en portait justement une (0,2 × 0,6 = 0,12 de blanc, invisible), elle se ternit désormais par ses couleurs, comme sa jumelle de `PhaseCard`. Corollaire de ce retrait : l'opacité couvrait aussi le survol de `.checkbox-card`, qui annonçait par un halo bleu un clic que la carte verrouillée ne rend pas — d'où un survol gardé pour les seules cartes cliquables, et une condition lue sur le **contrôle** (`.checkbox-card:hover:has(input:enabled)`) plutôt que sur un attribut à poser : un `:not([data-locked])` autorise par défaut, donc la carte ajoutée demain sans l'attribut annoncerait de nouveau un clic qu'elle ne rend pas — le « il faut s'en souvenir » que cette règle refuse partout ailleurs. Le `disabled` de la case dit déjà le fait, les deux écrans n'ont rien à redire — son cadre dit en outre **trois** choses et non deux (coché ou non, cliquable ou non), par une fonction unique partagée par les deux écrans (`checkboxCardChrome`, `app/(secured)/tournois/_lib/form-styles.ts`) : verrouillée, la carte portait sinon le chrome, au pixel près, d'une carte qui répond au clic. Et la bordure désactivée monte de 0,2 à **0,32** de blanc : `appearance: none` a retiré le carré que le système dessinait dessous, l'état est durable (le radio `START_TIME` de `MatchLiveDialog` l'est tant que le match n'a pas de date), et à 0,2 la case était un trou dans la page à côté de son étiquette.

- **Classement du site — cote de type Elo** (`lib/shared/ranking.ts` pur + `lib/server/ranking-service.ts`) : le cumul d'avant (100 par victoire, −20 par défaite) comptait des rencontres sans regarder **qui** était en face — battre la meilleure équipe du site et battre la dernière rapportaient pareil, et le premier du classement était simplement celui qui avait le plus joué. Chaque équipe part désormais de **500** et chaque match **transfère** des points du perdant au vainqueur (`ratingTransfer`, K = 32, échelle 400) : 500 qui bat 900 prend **29**, 900 qui bat 500 prend **3**. Trois choix, tous tenus par des tests : **K constant** (un K par équipe casserait la symétrie — le transfert est calculé une fois puis appliqué avec les deux signes), **plancher à 100** (seule entorse assumée à la conservation du total), et **une équipe sans match n'est pas classée** — tout le monde partant à 500, `compareRankedTeams` la range après les classées, sinon les équipes de remplissage occuperaient le milieu du tableau et les huit lignes du leaderboard. La cote dépendant de **l'ordre** des rencontres, elle se **rejoue** (`replayRanking`) comme `replaySurvival`/`replaySwiss` : rien n'est stocké, le classement est une **fonction pure** des matchs comptés, de leurs vainqueurs et de leurs dates. La chronologie (date du résultat puis identifiant du match) appartient au module pur, pas à l'`ORDER BY` — et la date étant `updated_at`, corriger un vieux score le **redate** : il se rejoue en dernier, pas à sa place d'origine (le contraire ferait diverger l'ordre du classement de celui des barres de forme). Conséquence : le SQL ne peut plus rendre les points — `rankingPointsForTeamSql` et les agrégats ont disparu, et les **quatre** requêtes de seeding (Survie, Suisse, Multi, aperçu) passent par `loadEntrantsBySiteRanking`, qui lit toujours sur **la connexion de l'appelant** — son option `transactional` ne règle que le droit de resservir une photo déjà prise : le seeding le refuse, l'aperçu (lecture seule) l'accepte. Le rejeu est mutualisé par `lib/server/ranking-cache.ts` (vol unique, TTL 60 s) et invalidé par les **trois** publications de `tournaments/notifications.ts`, événements de score compris : c'est le seul cache global qu'un score doive vider. Les entrées solo sont rejouées mais hors liste, les **équipes dissoutes** (`deleted_at`) aussi — elles ne sont plus à l'annuaire, et leur garder un rang faisait annoncer un total d'équipes classées que `/equipes` ne montre pas ; leurs matchs restent comptés, les retirer réécrirait la cote de toutes celles qui les ont affrontées. `getTeamRankingPosition` lit alors la cote sur **l'état rejoué** et non sur la valeur de départ, sinon une fiche afficherait 500 à côté d'un bilan de vingt matchs. Les fantômes restent classées, et une fiche **joueur** n'affiche plus de total de points (`DeepStats` n'en porte plus : un bilan ne suffit pas à déduire une cote — elle arrive par `TeamRankingPosition`). Voir `docs/features/ELO_RANKING.md`.
- **Points de parcours — ce qu'un tournoi rapporte pour le rang atteint** (`lib/shared/tournament-placement.ts` pur + rejeu dans `lib/shared/ranking.ts`) : la cote ne connaît que des rencontres, et chacune ne paie qu'à hauteur de sa **surprise** — une équipe forte qui gagne un tournoi en battant plus faible qu'elle empoche une dizaine de points quand une équipe moyenne sortie en demies sur une seule victoire improbable en encaisse le double. Le classement disait donc qu'**aller au bout coûte moins qu'être éliminé tôt** : juste à l'échelle d'un match, faux à celle d'un tournoi, qui désigne un **classement final** qu'aucun transfert pris isolément ne porte. À sa clôture, un tournoi met donc en jeu une **cagnotte** que ses engagées classées alimentent à parts égales (`cagnotte / effectif`) et que le rang final redistribue (`cagnotte × part(rang)`, poids en `1/place` normalisés). Trois propriétés, et rien d'autre à retenir : **somme nulle** — l'arrondi compris (troncature puis plus fort reste, ex æquo départagés par identifiant), la seule entorse restant le plancher, celui des défaites ; **le rang paie, pas l'exploit** — la part ne dépend **que** du rang, jamais de la cote de qui l'atteint, l'espérance ayant déjà eu son mot à dire match par match ; **la difficulté fixe l'enjeu** — `64 × √effectif × (cote moyenne du plateau / 500)`, bornée à [0,5 ; 2], la **moyenne** parce que ce qui rend un tournoi difficile est d'avoir à battre tout le monde, et la **racine** parce qu'un plateau quatre fois plus grand vaut deux fois plus et non quatre. Gagner un tournoi de 16 à difficulté moyenne rapporte 60 points, la dernière en perd 11. Les ex æquo se partagent les places qu'ils occupent **ensemble**, seule façon de garder la somme des parts à 1 — donc la somme nulle, dont tout dépend. **Aucune migration, rien de stocké** : `final_rank` et `finished_at` existent déjà, le barème s'applique rétroactivement, et le classement final est un **évènement du rejeu** comme un autre — trié par date puis par nature, les matchs **avant** les classements à date égale (la clôture est écrite dans la même transaction que le dernier score, la cagnotte doit se lire sur les cotes qu'il vient d'écrire). Une correction de score la défait donc seule. Restent dehors les tournois à moins de deux classées (écartés à la collecte : le tournoi clos faute d'adversaires déclare pourtant son unique inscrite première) et les tournois en cours ; et un classement final ne rend **pas** une équipe classée — `isRankedTeam` reste posé sur le bilan des matchs. `RankedTeamState.placementPoints` porte la part venue des parcours, **déjà comprise** dans `points`, jusqu'à une tuile « Points de parcours » de la fiche d'équipe qui ne s'affiche que si un tournoi clos l'a fait bouger. Voir `docs/features/TOURNAMENT_PLACEMENT_POINTS.md`.

Deux conséquences. Le prix est un **cookie** (`bg_recr_modal`, sept jours ; `bg_recr_banner`, la visite) à la place de `localStorage` : c'est le seul état de navigateur qu'une requête transporte, et le serveur doit savoir qui a déjà écarté l'annonce pour ne pas la réafficher — d'où leur mention sur `/rgpd`, la valeur n'étant que l'**identifiant de l'annonce**, jamais celui d'une personne (changer l'annonce mise en avant repart donc avec une clé neuve, comme la clé par annonce d'avant). Et le middleware pose le chemin demandé en en-tête (`PATHNAME_HEADER`), Next ne l'exposant à aucun composant serveur alors que la modale doit se taire sur `/recrutement` : décider après l'hydratation la ferait clignoter sur la page même où elle n'a rien à faire. `/api/recruitment/highlight` reste en place pour l'interface de gestion, mais ne sert plus au premier rendu — c'était un aller-retour sur **chaque page** du site, presque toujours pour rien.
- **Textes éditables de la vitrine** : titres, slogans et descriptions de `/` et `/association` sortent du JSX via le registre `lib/shared/site-copy.ts` (clé → libellé + valeur d'origine), sont stockés dans `bg_settings` (préfixe `copy_`) et s'éditent en place avec `<EditableCopy>` pour la permission `showcase`. Une clé absente ou vide retombe sur la valeur d'origine. Voir `docs/features/EDITABLE_SITE_COPY.md`.
- **Destination d'après connexion** (`lib/shared/safe-redirect.ts` pur) : le `?redirect=` de `/connexion` n'était contrôlé nulle part — `/connexion?redirect=https://exemple.invalid` déposait l'utilisateur **hors du site** une fois authentifié (redirection ouverte, l'appât classique du hameçonnage : vrai domaine, vraie page de connexion, et l'on ne part ailleurs qu'une fois la confiance acquise). La voie Google la reproduisait, la valeur traversant le cookie d'état OAuth pour ressortir par `new URL(redirectTo, base)` — **une base ne borne rien**, `new URL` l'ignore dès que la valeur est absolue. N'est accepté qu'un **chemin du site** : une seule barre en tête, donc ni `//exemple.invalid` (protocole-relative) ni `/\exemple.invalid` (que les navigateurs lisent pareil) ni un schéma exécutable ni un chemin relatif ; refus aussi de tout **caractère de contrôle** — les navigateurs retirent tabulation, saut de ligne et retour chariot avant de résoudre une URL, si bien qu'un saut de ligne glissé après la barre ferait redevenir `/…/exemple.invalid` une adresse protocole-relative. Filtré aux **trois** portes : la page de connexion, l'aller OAuth (avant écriture du cookie d'état) et le retour OAuth (le cookie n'est pas signé, il ne fait pas foi). `AuthGate` n'a rien à filtrer, sa destination venant de `usePathname()`. Voir `docs/features/SAFE_LOGIN_REDIRECT.md`.
- **Rôles de permission de plateforme** (cumulables, distincts des rôles d'équipe) : `ADMIN`, `ARBITRE` (tournois + diffusion), `CASTER` (aperçu du plateau en lecture seule + diffusion), `COMMUNITY_MANAGER` (site vitrine + association), `RECRUTEUR` (recrutement). Toujours protéger une route avec `can(user, "<permission>")` de `@/lib/shared/permissions` (permissions : `tournaments`, `casting`, `live`, `showcase`, `recruitment`, `roles`) — ne pas tester `user.isAdmin` directement pour un domaine scopé. `canAny(user, [...])` pour un accès ouvert à plusieurs domaines. `casting` ne donne **que** la lecture de l'aperçu ; `live` est le droit d'écriture sur l'état de diffusion. `ADMIN` a tous les droits. Voir `docs/features/PERMISSION_ROLES.md`.
- **Dates de début des matchs** (`lib/shared/match-schedule.ts` pur + `lib/server/tournaments/match-schedule.ts`) : chaque match porte son heure (`bg_matches.start_at`, `NULL` = aucun horaire annoncé), fixée par la permission `tournaments` (arbitre, admin) — **distincte de `live`** : un caster pose la chaîne d'un match, pas son horaire. La date est **descriptive** : elle n'avance pas le match, ne verrouille rien, n'entre dans aucune règle du moteur, et n'a donc **aucune garde d'état** en écriture (programmer un match déjà joué est une correction d'archive). Son seul effet est le mode d'antenne `START_TIME` (`LIVE` une fois l'heure atteinte sur un match jouable) — le seul état de diffusion qui bascule **sans écriture**, donc sans que le flux SSE puisse l'annoncer : `resolveMatchLiveState(match, now)` prend l'instant en argument, `nextMatchLiveChangeAt` donne la frontière, et `useMatchLiveState` en fait un unique `setTimeout` côté client (même principe que `useScheduledBuckets`). `START_TIME` sans date est refusé en 409 à l'écriture de la diffusion, mais effacer la date d'un match déjà casté reste permis — le calendrier n'est pas pris en otage par la diffusion, le match retombe à « programmé » et l'interface le signale. Voir `docs/features/MATCH_START_DATES.md`.
- **Messages Discord automatisés** (`lib/shared/discord-notifications.ts` pur + `lib/server/tournaments/match-reminders.ts` / `issue-reports.ts`) : le site **rédige**, le bot **distribue** — le sens des appels reste app → bot. Deux usages. (1) **Rappels de match** : une semaine, 24 h puis 1 h avant `bg_matches.start_at`, en message privé aux joueurs des deux engagées. Chaque palier ne vaut que dans **sa fenêtre** (`[début − palier, début − palier suivant)`), sans quoi une manche programmée à trente minutes déclencherait les trois rappels d'un coup. Une date posée **tardivement** ne rattrape pas les paliers manqués : elle donne une **annonce** unique portant la date, puis les paliers restants — le partage tient à la marque `SEEN`, posée à la première observation. Reprogrammer une manche efface ses rappels (`setMatchStartAt`), donc réannonce. Aucun ordonnanceur : le balayage est entraîné par le trafic depuis `listTournamentBuckets`, étranglé à 1 min, et la ligne `bg_match_reminders (match_id, offset_key)` est **réservée avant l'envoi** — c'est la clé unique qui interdit le doublon. Un joueur sans tag Discord est écarté silencieusement ; un joueur absent du serveur BlueGenji (`GUILD_ID` côté bot) ne reçoit **aucune tentative** d'envoi. (2) **Signalement d'un problème** : bouton dans l'en-tête du tournoi et sur chaque match, **réservé aux engagés** (`myTeamId`, revérifié serveur) ; part au canal de logs **et** au rôle arbitre configuré par `/set-referee-role`. Un bot injoignable est remonté en 503, jamais avalé. Voir `docs/features/DISCORD_NOTIFICATIONS.md`.
- **Journal d'activité Discord** (`lib/shared/bot-logs.ts` pur + `lib/server/tournaments/bot-logs.ts`) : le canal de logs du bot ne recevait que les conflits de score et les suppressions — un tournoi pouvait s'ouvrir, se remplir, se jouer et se conclure sans une ligne. Il reçoit désormais **une ligne par fait accompli** : **inscription d'un joueur sur le site**, création, inscription à un tournoi (joueur ou staff), abandon, coup d'envoi, **fin de match avec son score**, conflit, clôture (avec la championne), clôture faute d'adversaires, suppression. Deux règles de volume, tenues dans le module pur : **une ligne par évènement** (jamais un bloc) et **un évènement = un fait accompli** — la *fin* d'un match, pas les deux reports qui y mènent ; l'inscription, pas la visite de la page. Restent dehors byes, matchs fantômes, ouverture des inscriptions, programmation/diffusion/seeding/édition, et toute lecture : le nombre de lignes d'un tournoi reste de l'ordre de son nombre de matchs, qu'il ait trois spectateurs ou trois cents. Les évènements naissent **dans une transaction**, qui peut encore échouer : le moteur *réserve* une ligne (`queueBotLog`), le commit seul la convertit (`flushBotLogs`), l'échec la jette (`discardBotLogs` en `finally`). Une entrée n'est pas un texte mais un renvoi (« le match 42 s'est terminé ») : les noms, l'effectif et la championne sont relus **après** le commit — le classement final n'étant écrit qu'*après* `finishTournament`, une ligne rédigée sur place ne saurait pas encore qui a gagné. L'**inscription d'un joueur** est la seule ligne qui ne parle d'aucun tournoi — et la seule qu'un visiteur sans compte puisse provoquer. Le site n'ayant pas de formulaire d'inscription, un compte naît à la **première** connexion, par la même fonction qui retrouve les habitués les soirs suivants : elle est donc posée sur l'`INSERT` de `createOrGetGoogleUser` / `createOrGetDiscordUser` (`announcePlayerSignup`), là où « ce joueur est neuf » n'est pas une déduction — un compte existant auquel Google se rattache par son adresse vérifiée n'écrit rien. Hors transaction, donc envoyée directement par `sendBotLog` et sans être attendue, comme le retrait d'un engagé. Elle n'emploie **pas** le mot « inscription », déjà pris sur ce canal par l'engagement d'une équipe, et porte son propre pictogramme. Chaque évènement est posé au point de passage unique (`finalizeMatch`, `finishTournament`, `syncTournamentState`), jamais chez l'appelant. Voir `docs/features/BOT_ACTIVITY_LOG.md`.
- **Alertes au rôle arbitre** (`lib/shared/referee-alerts.ts` pur) : le journal complet est trop bavard pour arbitrer — un tournoi à 64 équipes y écrit une centaine de lignes, et la seule qui attend un geste s'y noie. Un **second canal** ne porte donc que ce qui appelle une intervention humaine, sous un critère unique : **un arbitre doit-il faire quelque chose en le lisant ?** Trois évènements le passent — **conflit de score** (le moteur ne départage pas deux reports contradictoires), **report expiré non tranché** (le délai ne clôt qu'une manche à *un seul* report : sur un conflit, il ne débloque rien) et **signalement d'un problème** (déjà sur ce canal). Restent au journal l'inscription, le coup d'envoi, la **fin de manche ordinaire** — c'est justement le cas où personne n'a eu à intervenir, et le plus nombreux —, l'abandon, la clôture (y compris faute d'adversaires) et la suppression. Le tri est un `Record` **exhaustif** sur `BotEventKind` : un évènement ajouté demain ne compile pas tant qu'il n'est pas classé, et **aucun appelant ne le connaît** — le moteur réserve comme avant (`queueBotLog`), c'est la file qui choisit le transport à l'envoi. Canal côté bot : `POST /internal/notify/referees`, **celui du signalement**, aucune route nouvelle — il poste au canal de logs *et* écrit en privé aux membres du rôle `/set-referee-role`. D'où l'invariant anti-doublon : **un évènement, un seul transport** (un conflit n'a plus de ligne de journal distincte, le bot en pose la trace lui-même). Messages d'**une ligne**, sans score ni effectif, avec le lien du tournoi ; le rôle est *nommé* (« Arbitrage requis »), pas mentionné — le site ne connaît pas son identifiant, qui se configure serveur par serveur. Les **deux** alertes sont réservées dans `bg_referee_alerts (match_id, alert_key)`, sur **la connexion de la transaction** (un rollback ne les consomme donc pas, contrairement aux rappels de match) : l'escalade parce qu'elle naît d'un **constat** refait à chaque entretien, le conflit parce que rien n'interdit aux engagées de resaisir leur score en boucle — `finalizeMatch` efface les réservations de la manche qu'il tranche, donc un désaccord qui renaît après arbitrage alerte de nouveau. Une réservation est **rendue** dès que l'alerte n'est pas partie (file pleine, entrée non résolue, bot injoignable) : sans palier suivant pour rattraper, un doublon vaut mieux qu'un silence définitif. Une réservation s'efface **par son identifiant de ligne**, jamais par sa paire de clés : la libération arrive jusqu'à 30 s plus tard, et un autre balayage a pu reposer la même paire entre-temps. Point d'entrée unique `queueRefereeAlert`, qui **ne lève jamais** et **ne réserve rien tant que le coupe-circuit est ouvert** (sinon la panne ferait tourner une pompe d'`INSERT`/`DELETE`, le constat se refaisant à chaque lecture) : réservation inaccessible → le conflit part quand même sans marque (une par action d'un joueur, comme avant ce canal), l'escalade se tait (elle partirait en boucle). `finalizeMatch` retire de la **file en mémoire** (sans écriture) les alertes de la manche qu'il tranche — le même appel peut réserver une escalade puis clore la manche, et le commit annoncerait sinon qu'un match `COMPLETED` n'est pas tranché ; l'effacement des lignes suit le commit, sur le pool, pour ne pas poser un verrou de plus sur le chemin le plus chaud du moteur. Seule exception au « ne lève jamais » : ce qui a **déjà défait la transaction** (interblocage) est **relancé** — l'avaler ferait commiter sur une écriture disparue (`lib/server/mysql-errors.ts`). Le délai de l'escalade court depuis `score_deadline_at` (posé au premier report et jamais réécrit, donc non repoussable par une resaisie) plus un délai, et `flushBotLogs` écarte l'escalade quand le conflit part dans la même file — règle posée sur la file entière, `resolveExpiredScoreReports` étant appelée deux fois par report, avant *et* après la mise en file du conflit. Dégradation : bot injoignable → `null`, rôle non configuré → le bot répond 200 et se contente du log, et le **coupe-circuit est respecté** ici (à l'inverse du signalement, action utilisateur à qui l'on doit une tentative). Voir `docs/features/REFEREE_ALERTS.md`.
- **« Live » / « Direct » — trois sens à ne jamais confondre dans les libellés** : le projet emploie le mot pour (1) l'**état d'un tournoi** `RUNNING`, (2) une **diffusion** (stream Twitch/YouTube/Kick d'un tournoi ou d'un match), (3) la **connexion au flux SSE** qui tient la page à jour. Les trois se côtoyaient sur la même ligne de pastilles de `/tournois/[id]`, où « ● DIRECT » (connexion) voisinait « ● EN COURS » (état) sur un tournoi sans la moindre chaîne — on y lisait un stream qui n'existait pas. Règle de vocabulaire, sans effet sur le code interne (les valeurs `MatchLiveState`, les noms de fichiers `*live*` et les classes `pill-live` restent) : **« En cours »** pour l'état d'un tournoi (jamais « Live » ni « En direct »), **« En direct » / « le live »** réservé à une vraie diffusion, **« À jour » / « Reconnexion… » / « Hors ligne »** pour le témoin de flux (`LiveIndicator`). Le **rouge** (`pill-live`, `--red-live`) n'habille que ce qui est réellement à l'antenne : un état de tournoi ou un témoin de connexion se met en bleu. Avant d'écrire « Live » ou « Direct » dans une interface, se demander lequel des trois on désigne.
- **Diffusion en direct** (`lib/shared/live-streams.ts` pur + `lib/server/tournaments/live-streams.ts`) : le tournoi porte sa **chaîne officielle** (`bg_tournaments.live_url`), chaque match porte sa propre diffusion (`live_trigger` `AUTO`/`MANUAL`, `live_url`, `live_started_at`) — **un match n'hérite jamais** de la chaîne du tournoi, parce qu'un streamer indépendant peut le caster. L'état (`OFF`/`SCHEDULED`/`LIVE`) n'est **pas stocké** : `resolveMatchLiveState` le dérive, si bien que l'arrêt du direct à la saisie du score ne demande aucune écriture et qu'une correction de score le défait seule. Aucune requête ne réimplémente la règle en SQL — `findBroadcastingTournament` filtre en mémoire avec `isMatchLive`. Le bouton « Regarder le live » de l'accueil n'est rendu **que si** un tournoi `RUNNING` a une chaîne officielle et au moins un match `LIVE` ; sinon il disparaît. URLs bornées par une liste blanche (`twitch.tv`, `youtube.com`, `youtu.be`, `kick.com`). Voir `docs/features/LIVE_STREAMS.md`.

## Règles de travail

### Tests
- Chaque feature développée doit être accompagnée d'une couverture de tests complète et efficace (`npm test`).
- Les tests doivent couvrir les cas nominaux, les cas limites et les cas d'erreur.
- Aucune feature n'est considérée comme terminée sans ses tests associés.

### Branches
- Pour chaque demande de feature, créer une branche dédiée : `feature/<nom-de-la-feature>` (kebab-case, anglais de préférence).
- Exemple : `feature/swiss-pairing`, `feature/discord-login`.

### Pull Requests
- À l'achèvement d'une feature, ouvrir une Pull Request vers `main`.
- Si le CI de la PR échoue, tenter de corriger automatiquement dans cet ordre : lint → build → tests.
- Si une erreur ne peut pas être corrigée automatiquement, l'expliquer clairement et proposer une piste de résolution.

### CI / Qualité
- Le CI GitHub Actions (`.github/workflows/ci.yml`) vérifie à chaque PR : lint → build → tests (dans cet ordre, enchaînés via `needs:`).
- Ne pas merger si le CI est rouge.

### Erreurs préexistantes (`ERREUR.txt`)
- Toute erreur rencontrée mais **non réglée parce qu'elle préexiste** à la tâche en cours (bug déjà présent sur `main`, hors périmètre de la feature) doit être consignée dans `ERREUR.txt`, à la racine du dépôt, pour être traitée plus tard.
- Ne jamais élargir silencieusement le périmètre d'une tâche pour corriger un problème préexistant : le noter dans `ERREUR.txt`, le signaler dans le résumé de fin, puis poursuivre.
- Une entrée par erreur, ajoutée à la fin du fichier, au format :
  ```
  - [AAAA-MM-JJ] <fichier:ligne ou zone> — <symptôme observé> — <cause supposée / piste> — (rencontré sur : <branche ou PR>)
  ```
- Avant d'ajouter une entrée, vérifier qu'elle n'y figure pas déjà ; le cas échéant, compléter l'entrée existante plutôt que d'en créer une seconde.
- Retirer l'entrée du fichier dans le commit qui règle enfin l'erreur.

### Gestion de la complexité
- Pour toute demande importante (≥ 2 features liées, refactoring architectural, intégration d'un nouveau service externe, ou tâche estimée > ~2h), établir d'abord un plan écrit (étapes ordonnées, fichiers touchés, points de vérification), puis l'exécuter dans cette session.
- Ne pas déléguer ce travail à un pipeline d'exécution externe ou à un modèle local (`/OpusLocalManager`, `/opus-haiku-pipeline`) : la planification et l'exécution restent dans la session courante.

### Dépôt voisin `blueGenjiBot`

Une partie du travail de ce projet se fait dans le dépôt du bot (`../blueGenjiBot`, surchargeable par `BOT_DOCS_PATH`). Deux obligations y suivent le code, et elles ne se recouvrent pas :

- **La doc Markdown du bot est en ligne sans déploiement.** `doc/*.md`, `help.md` et `helpfr.md` sont lus **à chaud** par `lib/server/bot-docs.ts` et publiés sur `/bot/docs` (registre `BOT_DOC_SECTIONS`, revalidation 60 s). Toucher une commande du bot sans corriger son Markdown met le site en contradiction avec le bot dans la minute qui suit — aucun rebuild ne fait écran, et aucun test ne le verra.
- **La référence JSDoc (`docs/`) se régénère dans la même PR que le code.** Toute PR du bot qui touche `src/` — ajout, renommage, suppression d'un module, ou réécriture d'un bloc JSDoc — vide `docs/` puis relance `npm run docs`, et commite le résultat **à part** (chaque page porte son horodatage de génération, l'arbre entier ressort modifié à chaque passage). Sans le ménage préalable, la page d'un module supprimé survit indéfiniment. Détail des pièges : section « Documentation » du `CLAUDE.md` du bot.

Ne pas confondre les deux dossiers : `doc/` est le Markdown servi par le site, `docs/` la référence HTML générée.

## Pipeline Git (workflow de livraison)

Chaque tâche : quatre commits sur une branche de feature, puis une revue de PR.

**Règle Co-Authored-By :**
- **Tous** les commits (fonctionnel, docs, tests, polish) portent un trailer `Co-authored-by: <modèle> <noreply@anthropic.com>`.
- **`<modèle>` est le modèle qui écrit réellement le commit**, jamais une valeur recopiée : `Claude Opus 5`, `Claude Sonnet 5`, `Claude Opus 4.8`, selon le cas. Cette ligne a longtemps nommé `Claude Opus 4.8` en dur, et elle a continué d'être suivie à la lettre bien après : des commits écrits par un autre modèle portent donc une attribution fausse. Un co-auteur inexact vaut moins qu'aucun — c'est précisément ce que le trailer sert à dire.
- Se relire sur ce point **au premier commit d'une session**, pas au cinquième : quatre commits à réécrire, c'est un historique qu'on ne corrige plus.

Enchaîner la pipeline **sans s'arrêter** : ne pas attendre de validation de l'utilisateur après le commit fonctionnel — dérouler les commits, le push et la PR d'affilée.

Ajouter le trailer avec `git commit --trailer 'Co-authored-by: <modèle> <noreply@anthropic.com>'` — par exemple `git commit --trailer 'Co-authored-by: Claude Opus 5 <noreply@anthropic.com>'`.

1. **Branche de feature** : `git checkout -b feature/<short-name>`
2. **Commit fonctionnel** : ≤ 5 mots, impératif minuscule — `add swiss pairing` — *avec Co-Authored-By*
3. **Commit docs** : README / JSDoc limité à ce qui a été construit — *avec Co-Authored-By*
4. **Commit tests** : `jest` — *avec Co-Authored-By*
5. **Commit polish UI/UX** : espacements, états, accessibilité — aucun changement de logique — *avec Co-Authored-By*
6. **Push** : `git push -u origin feature/<short-name>`
7. **Revue de PR — en boucle jusqu'à zéro finding** : ouvrir la PR (`gh pr create`), puis lancer une revue du diff avec `/code-review --comment` pour poster les retours en **commentaires inline** sur la PR.

   **Cycler la revue** : corriger les points remontés, commiter, pousser, puis **relancer une revue complète**. Répéter jusqu'à ce qu'un cycle ne remonte plus aucun finding. Une seule passe ne suffit pas : les corrections d'un cycle en révèlent d'autres, et les zones non couvertes par le premier passage doivent l'être par les suivants.

   Ne rendre la main à l'utilisateur qu'une fois un cycle terminé **sans finding**, avec `npm test`, `npm run lint` et `npx tsc --noEmit` verts.

   **Valider aussi en conditions réelles** : les tests simulent MySQL et ne peuvent pas détecter une colonne manquante ou une requête invalide. Lancer `npm run seed` avant de conclure — c'est le seul contrôle qui exerce réellement les migrations et le SQL. (Le worktree a besoin d'une copie du `.env` du dépôt parent ; il est déjà couvert par `.gitignore`.)
